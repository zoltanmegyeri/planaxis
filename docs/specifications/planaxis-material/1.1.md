# PlanAxis Material Format Specification

**Version:** 1.1  
**Status:** Normative specification  
**Language:** English  
**Schema identifier:** `planaxis-material/1.1`

---

# 1. Purpose and scope

This document defines **PlanAxis Material Format 1.1**, the persistent renderer-independent format used to describe a reusable project-local surface material within a PlanAxis project.

A Material 1.1 descriptor represents one normalized material resource suitable for assignment to architectural finish targets through PlanAxis Design Format.

Version 1.1 supports one unified metallic/roughness PBR-oriented material model with:

- optional base-color factor;
- optional roughness factor;
- optional metalness factor;
- optional ambient-occlusion strength;
- optional base-color texture map;
- optional roughness texture map;
- optional metalness texture map;
- optional tangent-space normal map;
- optional ambient-occlusion texture map;
- common physical texture width and height;
- opaque, masked, and blended alpha behavior.

Material 1.1 extends Material 1.0 with ambient-occlusion support. It adds:

- `maps.ambientOcclusion`;
- `ambientOcclusionStrength`.

All other Material 1.0 concepts remain unchanged unless this specification explicitly states otherwise.

The format deliberately separates:

```text
material definition
    from
surface assignment
    from
renderer implementation state
```

The material descriptor defines reusable material appearance and physical texture scale. It does not identify which architectural surface uses the material.

PlanAxis Design Format owns finish-target-to-material assignment.

Material 1.1 deliberately does **not** define:

- finish-target identity;
- per-assignment texture rotation, mirroring, offset, or other mapping overrides;
- material inheritance;
- material variants;
- material categories, style tags, manufacturer metadata, or product metadata;
- displacement or height maps;
- emissive maps;
- clearcoat;
- anisotropy;
- sheen;
- transmission;
- subsurface scattering;
- environment maps;
- lighting;
- 3D model assets;
- UI workflows for importing, discovering, creating, editing, or deleting materials;
- AI-assisted material extraction or generation.

Those concerns may be introduced by later formats or later application features when their semantics are concrete.

# 2. Normative keywords

The key words **REQUIRED / MUST**, **MUST NOT**, **SHOULD**, **SHOULD NOT**, **MAY**, and **OPTIONAL** are normative.

- **REQUIRED / MUST** — mandatory for conformance.
- **MUST NOT** — prohibited.
- **SHOULD** — recommended unless a documented reason justifies deviation.
- **SHOULD NOT** — discouraged unless a documented reason justifies deviation.
- **MAY / OPTIONAL** — permitted but not required.

If an example conflicts with a normative rule, the normative rule takes precedence.

# 3. Relationship to other PlanAxis formats

PlanAxis Material Format is versioned independently from:

- PlanAxis Project Format;
- Apartment SVG;
- PlanAxis Design Format;
- future PlanAxis model-asset formats;
- the PlanAxis application version.

A project may therefore combine versions independently, for example:

```text
PlanAxis Project Format 1.0
Apartment SVG 2.2
PlanAxis Design Format 1.0
PlanAxis Material Format 1.1
```

## 3.1. PlanAxis Project Format

A material descriptor and its texture resources exist inside a filesystem-backed PlanAxis project and use the project-relative path and filesystem-boundary rules defined by the applicable PlanAxis Project Format specification.

PlanAxis Project Format 1.0 reserves:

```text
assets/materials/
```

for normalized material resources.

Material Format 1.1 gives material descriptors and their supported texture resources concrete semantics without changing the root project manifest.

## 3.2. Apartment SVG

Apartment SVG remains the source of architectural and geometric truth.

A material descriptor MUST NOT duplicate or override architectural facts such as:

- walls;
- spaces;
- openings;
- dimensions;
- floor or ceiling geometry;
- finish-target geometry.

Material physical texture dimensions describe the repeating physical size of material imagery. They are not apartment geometry.

Ambient occlusion is appearance data. It MUST NOT alter Apartment SVG geometry, architectural dimensions, collision geometry, finish-target identity, or any other architectural fact.

## 3.3. PlanAxis Design Format

PlanAxis Design Format 1.0 assigns a project-local `material` resource reference to a finish target.

Design Format 1.0 deliberately validates only that the material reference is a valid project-relative path under:

```text
assets/materials/
```

Design Format 1.0 does not require that the referenced path:

- exists;
- is a regular file;
- uses `.json`;
- conforms to Material Format 1.1;
- resolves all texture resources;
- can be rendered.

For a Design 1.0 finish assignment to resolve specifically as a Material 1.1 material, its `material` path MUST identify a Material 1.1 descriptor satisfying this specification.

Therefore a design may remain Design 1.0-format conformant while material resolution fails.

Material Format 1.1 does not change Design Format 1.0 structural conformance rules.

## 3.4. Relationship to Material 1.0

Material 1.0 remains a valid independently versioned schema.

A descriptor whose `schema` is:

```text
planaxis-material/1.0
```

remains a Material 1.0 descriptor and MUST NOT be reinterpreted as Material 1.1 merely because a consumer also supports Version 1.1.

A consumer MAY support both versions and normalize their compatible semantics into a common in-memory representation.

A Material 1.0 descriptor that requires ambient occlusion must be explicitly migrated to Material 1.1 by changing its schema and adding the new Version 1.1 properties as needed.

## 3.5. References versus normalized assets

Files under:

```text
references/
```

are source or inspiration material and do not become Material 1.1 assets merely because they visually depict a real material.

Examples include:

- webshop photographs;
- manufacturer photographs;
- screenshots;
- sample photographs;
- AI-generation inputs.

A usable Material 1.1 asset is an explicit normalized resource under `assets/materials/` with a conforming material descriptor.

# 4. Conformance and resolution levels

Material processing is examined at distinct levels.

## 4.1. JSON-conformant

The descriptor file contains syntactically valid JSON representing exactly one JSON object.

## 4.2. Material-format conformant

The JSON object and descriptor path satisfy all structural and lexical rules of `planaxis-material/1.1`, including:

- supported schema identifier;
- descriptor location;
- closed object structures;
- required properties;
- numeric constraints;
- map/mapping relationship;
- ambient-occlusion map/strength relationship;
- alpha variant rules;
- project-relative texture path syntax;
- supported texture filename extensions.

Material-format conformance does not prove that referenced texture files exist or can be decoded.

## 4.3. Project-resolved

A Material 1.1 descriptor is project-resolved when every referenced texture resource:

- resolves through the project filesystem boundary;
- remains within the canonical project root;
- is reached without prohibited symbolic-link traversal;
- identifies an accessible regular file;
- is located under `assets/materials/`;
- retains the supported lowercase filename extension declared by the descriptor.

Project resolution does not prove that the file bytes actually contain a decodable image of the expected supported format.

## 4.4. Texture-resolved

A project-resolved material is texture-resolved when every referenced texture resource can be successfully loaded and decoded as one of the supported image formats defined by this specification.

A filename extension alone is not sufficient evidence of successful texture resolution.

## 4.5. Renderer-adapted

A texture-resolved material is renderer-adapted when an application has translated its renderer-independent semantics into the active rendering backend and established the required runtime texture resources.

Renderer adaptation is outside Material Format conformance.

GPU objects, renderer-specific classes, texture handles, upload settings, UV-channel selections, and backend constants MUST NOT be serialized into a Material 1.1 descriptor.

## 4.6. Failure separation

Implementations SHOULD preserve useful distinctions between:

- invalid JSON;
- Material 1.1 structural failure;
- invalid descriptor identity/path;
- project-resource failure;
- missing texture;
- unsupported or mismatched texture content;
- image decode failure;
- renderer adaptation failure.

A later failure MUST NOT retroactively be reported as malformed Material 1.1 JSON when the descriptor itself is structurally conformant.

# 5. Terminology

## 5.1. Material descriptor

A **material descriptor** is a JSON file under `assets/materials/` that conforms to this specification.

## 5.2. Material asset

A **material asset** is the normalized project-local material resource represented by one material descriptor together with any texture resources referenced by that descriptor.

## 5.3. Material identity

The project-relative path of the material descriptor is its durable identity within the project.

No separate internal material ID exists in Version 1.1.

## 5.4. Material name

The `name` field is a human-readable display label only.

It is not:

- an identifier;
- a filesystem name;
- a uniqueness key;
- a reference target.

## 5.5. Texture resource

A **texture resource** is a supported PNG, JPEG, or WebP image file referenced by a Material 1.1 descriptor.

## 5.6. Physical texture period

The **physical texture period** is the real-world width and height represented by one complete repetition of the texture imagery.

For example:

```text
widthCm = 120
heightCm = 20
```

means one full horizontal repeat represents 120 cm and one full vertical repeat represents 20 cm in the material mapping frame.

The physical texture period is independent from pixel resolution.

## 5.7. Ambient occlusion

**Ambient occlusion** is local material appearance data describing how strongly ambient or indirect illumination is attenuated in small-scale recessed or occluded regions of the material.

Ambient occlusion is not:

- a replacement for explicit light sources;
- a replacement for cast shadows;
- architectural geometry;
- a height or displacement representation;
- a source of direct-light shadowing.

# 6. Descriptor location, identity, and encoding

## 6.1. Location

A Material 1.1 descriptor MUST be stored at a project-relative path under:

```text
assets/materials/
```

The filename MUST use the lowercase `.json` extension.

Examples:

```text
assets/materials/oak-natural/material.json
assets/materials/paint/warm-white.json
assets/materials/tiles/bathroom/matte-stone.json
```

No additional filename or directory convention is required by Version 1.1.

The recommended organization is to keep one material descriptor and its texture maps together when practical:

```text
assets/materials/oak-natural/
├── material.json
├── base-color.webp
├── normal.webp
├── roughness.webp
└── ambient-occlusion.webp
```

This organization is recommended, not required.

## 6.2. Identity

The descriptor's complete project-relative path is its identity.

For example:

```text
assets/materials/oak-natural/material.json
```

and:

```text
assets/materials/archive/oak-natural/material.json
```

identify different material assets even if their JSON contents are identical.

Moving or renaming a material descriptor therefore changes its identity.

## 6.3. Encoding

The descriptor MUST contain UTF-8 encoded JSON representing exactly one JSON object.

A byte-order mark SHOULD NOT be written.

---

# 7. Project-relative path rules

All persistent paths in a Material 1.1 descriptor MUST use the project-relative path syntax defined by the applicable PlanAxis Project Format specification.

A project-relative path MUST NOT:

- be empty;
- begin with `/`;
- contain `\`;
- contain an empty path segment;
- contain a `.` path segment;
- contain a `..` path segment;
- contain a NUL character;
- contain a URI scheme such as `file:`;
- contain a Windows drive prefix such as `C:`;
- otherwise represent or resolve as an absolute filesystem path.

Persistent paths use `/` as the separator on every operating system.

Texture references are always project-relative.

Descriptor-relative texture references are not supported.

For example, inside:

```text
assets/materials/oak-natural/material.json
```

this is invalid:

```json
"baseColor": "base-color.webp"
```

and this is valid:

```json
"baseColor": "assets/materials/oak-natural/base-color.webp"
```

---

# 8. Closed-schema rule

PlanAxis Material Format 1.1 is recursively closed.

Unknown properties are PROHIBITED:

- at the root object;
- inside `mapping`;
- inside `maps`;
- inside `alpha`.

Version 1.1 defines no `x-*`, `data-x-*`, or other extension-property mechanism.

A future format version may add properties explicitly.

---

# 9. Root object

The root JSON object supports exactly these properties:

| Property | Type | Required | Meaning |
|---|---|---:|---|
| `schema` | string | yes | schema identifier |
| `name` | string | yes | human-readable display name |
| `baseColor` | RGB tuple | no | scalar base-color factor |
| `roughness` | number | no | scalar roughness factor |
| `metalness` | number | no | scalar metalness factor |
| `ambientOcclusionStrength` | number | conditional | strength of the ambient-occlusion map |
| `mapping` | object | conditional | common physical texture period |
| `maps` | object | no | texture-resource references |
| `alpha` | object | no | alpha behavior |

`ambientOcclusionStrength` is permitted only when `maps.ambientOcclusion` exists.

A representative descriptor is:

```json
{
  "schema": "planaxis-material/1.1",
  "name": "Natural oak",
  "baseColor": [1, 1, 1],
  "roughness": 0.7,
  "metalness": 0,
  "ambientOcclusionStrength": 0.8,
  "mapping": {
    "widthCm": 120,
    "heightCm": 20
  },
  "maps": {
    "baseColor": "assets/materials/oak-natural/base-color.webp",
    "normal": "assets/materials/oak-natural/normal.webp",
    "roughness": "assets/materials/oak-natural/roughness.webp",
    "ambientOcclusion": "assets/materials/oak-natural/ambient-occlusion.webp"
  }
}
```

The minimum conforming root object contains only:

```json
{
  "schema": "planaxis-material/1.1",
  "name": "Material name"
}
```

---

# 10. `schema`

`schema` is REQUIRED.

Its value MUST be exactly:

```text
planaxis-material/1.1
```

An implementation that does not support the schema identifier MUST reject Material Format interpretation and MUST NOT guess the semantics of the document.

---

# 11. `name`

`name` is REQUIRED.

Its value MUST be a JSON string containing at least one non-whitespace Unicode character after trimming.

The stored value is the human-readable material name.

The `name`:

- MAY be duplicated by another material descriptor;
- MAY differ from the descriptor filename or directory name;
- MUST NOT be used as persistent identity.

---

# 12. Scalar PBR properties

Material 1.1 uses one metallic/roughness PBR-oriented material model.

The scalar properties in this section are OPTIONAL subject to their stated conditions.

When omitted, the unconditional normative defaults are:

```text
baseColor = [1, 1, 1]
roughness = 1
metalness = 0
```

When `maps.ambientOcclusion` is present and `ambientOcclusionStrength` is omitted:

```text
ambientOcclusionStrength = 1
```

These defaults are part of Material Format semantics.

They are not renderer-specific defaults.

## 12.1. `baseColor`

`baseColor` is OPTIONAL.

If present, it MUST be a JSON array containing exactly three finite JSON numbers:

```text
[R, G, B]
```

Each component MUST be in the inclusive range:

```text
0 <= component <= 1
```

The values represent an sRGB base-color factor.

Examples:

```json
"baseColor": [1, 1, 1]
```

```json
"baseColor": [0.88, 0.84, 0.76]
```

When omitted:

```text
baseColor = [1, 1, 1]
```

## 12.2. `roughness`

`roughness` is OPTIONAL.

If present, it MUST be a finite JSON number in the inclusive range:

```text
0 <= roughness <= 1
```

When omitted:

```text
roughness = 1
```

## 12.3. `metalness`

`metalness` is OPTIONAL.

If present, it MUST be a finite JSON number in the inclusive range:

```text
0 <= metalness <= 1
```

When omitted:

```text
metalness = 0
```

## 12.4. `ambientOcclusionStrength`

`ambientOcclusionStrength` is OPTIONAL only when `maps.ambientOcclusion` is present.

If present, it MUST be a finite JSON number in the inclusive range:

```text
0 <= ambientOcclusionStrength <= 1
```

If `maps.ambientOcclusion` exists and `ambientOcclusionStrength` is omitted:

```text
ambientOcclusionStrength = 1
```

If `maps.ambientOcclusion` does not exist, `ambientOcclusionStrength` MUST be absent.

The value controls how strongly the ambient-occlusion map attenuates ambient or indirect illumination:

```text
0 = ambient-occlusion map has no effect
1 = ambient-occlusion map is applied at full strength
```

Intermediate values linearly interpolate between no occlusion and the sampled occlusion value.

## 12.5. Scalar and texture-map combination

When a corresponding texture map is present, scalar factors and map samples combine using ordinary metallic/roughness PBR factor semantics.

Conceptually:

```text
effective base color = baseColor factor × decoded base-color map RGB
effective roughness  = roughness factor × roughness-map channel
effective metalness  = metalness factor × metalness-map channel
```

For ambient occlusion:

```text
effective ambient occlusion
    = 1 - ambientOcclusionStrength × (1 - ambient-occlusion-map channel)
```

Equivalently:

```text
effective ambient occlusion
    = mix(1, ambient-occlusion-map channel, ambientOcclusionStrength)
```

The resulting value is used to attenuate ambient or indirect illumination according to the renderer's physically based lighting model.

The ambient-occlusion result MUST NOT be interpreted as direct-light visibility or as a cast-shadow mask.

Color-space conversion required for correct PBR rendering occurs before the renderer evaluates the effective linear-light shading values.

The formulas above express domain intent rather than prescribing a specific renderer implementation.

Because the default `metalness` factor is `0`, a material that intends to use a metalness texture MUST explicitly choose a non-zero `metalness` factor, normally:

```json
"metalness": 1
```

when the texture should control the full metallic range.

# 13. `maps`

`maps` is OPTIONAL.

If present:

- it MUST be a JSON object;
- it MUST contain at least one supported property;
- it MUST contain no unknown properties;
- `mapping` MUST also be present.

An empty `maps` object is PROHIBITED.

Supported properties are:

| Property | Type | Required | Meaning |
|---|---|---:|---|
| `baseColor` | string | no | sRGB base-color texture |
| `roughness` | string | no | non-color roughness texture |
| `metalness` | string | no | non-color metalness texture |
| `normal` | string | no | non-color tangent-space normal texture |
| `ambientOcclusion` | string | no | non-color ambient-occlusion texture |

At least one property MUST be present whenever `maps` exists.

Different map roles MAY reference the same texture resource.

This allows packed source images where the relevant channels are interpreted independently.

In particular, a conventional packed ORM image MAY be referenced by all three of:

```text
maps.ambientOcclusion
maps.roughness
maps.metalness
```

because Material 1.1 reads:

```text
ambient occlusion -> red channel
roughness         -> green channel
metalness         -> blue channel
```

## 13.1. Common map alignment

All maps in one descriptor represent the same physical texture period and mapping orientation.

Version 1.1 defines:

- one common `mapping.widthCm`;
- one common `mapping.heightCm`;
- one common architectural material mapping frame supplied by the finish target;
- no per-map scale;
- no per-map rotation;
- no per-map mirroring;
- no per-map offset.

Texture images used by one material MAY have different pixel resolutions, but they MUST be authored so their visual features align over the same physical period.

The ambient-occlusion map therefore uses the same physical material mapping frame as the base-color, roughness, metalness, and normal maps. Material 1.1 defines no separate ambient-occlusion UV set or mapping period.

---

# 14. `mapping`

`mapping` is conditionally REQUIRED.

Rules:

- if `maps` is present, `mapping` MUST be present;
- if `maps` is absent, `mapping` MUST be absent.

A scalar-only material therefore does not store unused physical texture dimensions.

`mapping` is a closed JSON object containing exactly:

| Property | Type | Required | Meaning |
|---|---|---:|---|
| `widthCm` | number | yes | physical width of one complete texture repeat |
| `heightCm` | number | yes | physical height of one complete texture repeat |

Example:

```json
"mapping": {
  "widthCm": 120,
  "heightCm": 20
}
```

## 14.1. Numeric constraints

`widthCm` and `heightCm` MUST each be finite JSON numbers strictly greater than zero.

They use ordinary JSON numeric semantics.

Material Format is not an authoritative architectural geometry format, so Apartment SVG's exact-decimal persistence policy does not apply to these values.

Implementations MAY convert validated values into another internal numeric representation when adapting the material to an existing renderer-independent runtime contract.

## 14.2. Physical meaning

The complete horizontal image period corresponds to `widthCm`.

The complete vertical image period corresponds to `heightCm`.

For a mapping frame with physical coordinates `(uCm, vCm)`, the repeating texture coordinates are conceptually:

```text
u = uCm / widthCm
v = vCm / heightCm
```

Values below zero and values above one are valid and repeat naturally.

Texture phase is determined by the finish target's stable physical mapping frame, not by individual render patches.

## 14.3. Orientation

Material 1.1 stores no rotation or orientation override.

For every texture map:

- visual image right corresponds to mapping `+U`;
- visual image up corresponds to mapping `+V`.

The image-loading/runtime adapter is responsible for configuring source-image upload orientation so these semantics hold.

A future design-level finish-assignment extension may introduce per-assignment orientation or mapping overrides.

Such an override MUST NOT be inferred into Material 1.1.

---

# 15. Texture-resource references

Every map property MUST be a project-relative path that:

- follows section 7;
- begins with `assets/materials/`;
- identifies a filename using one supported lowercase extension from section 16.

Examples:

```text
assets/materials/oak-natural/base-color.webp
assets/materials/oak-natural/normal.png
assets/materials/shared/roughness.jpg
assets/materials/concrete/ambient-occlusion.webp
```

The referenced texture:

- does not have to be stored beside the descriptor;
- MAY be shared by multiple materials;
- MAY be reused by multiple map roles;
- MUST NOT use a descriptor-relative path.

Material-format conformance validates the path and extension only.

Filesystem existence and image decoding belong to later resolution stages.

---

# 16. Supported texture formats

Material Format 1.1 supports exactly these texture image formats and lowercase filename extensions:

| Format | Extensions |
|---|---|
| PNG | `.png` |
| JPEG | `.jpg`, `.jpeg` |
| WebP | `.webp` |

No other texture format is defined by Version 1.1.

In particular, the following are not supported Material 1.1 texture resources:

- AVIF;
- GIF;
- SVG;
- TIFF;
- BMP;
- HDR/RGBE;
- OpenEXR;
- DDS;
- KTX/KTX2;
- arbitrary binary images without a supported extension.

A future Material Format version may add formats explicitly.

## 16.1. Extension and content

A supported filename extension is required for Material-format conformance.

Texture resolution additionally requires successful decoding of the referenced bytes as a supported image.

An implementation MUST NOT treat arbitrary undecodable bytes as a resolved texture merely because the filename extension is allowed.

# 17. Texture-map semantics

## 17.1. Base-color map

`maps.baseColor` is interpreted as sRGB color data.

Its RGB channels supply the base-color texture factor.

If the image format contains an alpha channel, that alpha channel supplies the sampled source alpha used by section 19.

If the decoded image has no alpha channel, sampled source alpha is:

```text
1
```

## 17.2. Roughness map

`maps.roughness` is non-color data.

The roughness value is read from the texture's **green channel**.

The texture MUST NOT be interpreted as sRGB color data.

## 17.3. Metalness map

`maps.metalness` is non-color data.

The metalness value is read from the texture's **blue channel**.

The texture MUST NOT be interpreted as sRGB color data.

## 17.4. Normal map

`maps.normal` is non-color tangent-space normal data.

The decoded normal basis is:

```text
+X = mapping +U
+Y = mapping +V
+Z = outward physical surface normal
```

The conventional RGB encoding maps stored channel values from `[0, 1]` into tangent-space components in `[-1, 1]`.

A normal map authored with the opposite Y convention must be converted before use as a conforming Material 1.1 resource.

Version 1.1 defines no per-material or per-assignment "flip normal Y" property.

## 17.5. Ambient-occlusion map

`maps.ambientOcclusion` is non-color data.

The ambient-occlusion value is read from the texture's **red channel**.

The texture MUST NOT be interpreted as sRGB color data.

The sampled channel has this meaning:

```text
1 = fully unoccluded ambient/indirect illumination
0 = maximally occluded ambient/indirect illumination
```

Values between `0` and `1` represent partial occlusion.

The sampled value is combined with `ambientOcclusionStrength` according to section 12.5.

Ambient occlusion is local material shading information only. It does not modify geometry, surface normals, direct-light visibility, or explicit shadow geometry.

---

# 18. Texture repetition and transforms

All texture maps repeat over the physical mapping frame according to section 14.

Version 1.1 defines no persistent texture transform properties.

The descriptor MUST NOT contain:

- repeat counts;
- UV offsets;
- rotation angles;
- mirror flags;
- arbitrary UV matrices;
- per-map UV-channel selectors;
- renderer texture-transform objects.

Repeat density is determined only by:

```text
physical surface mapping distance
÷
mapping width/height
```

This preserves real-world material scale independently of surface size and renderer tessellation.

Renderer adapters MAY use whatever backend UV attribute or texture channel is required to realize the common Material 1.1 mapping semantics. Such backend selection is not persistent material state.

---

# 19. `alpha`

`alpha` is OPTIONAL.

If omitted, the material uses opaque alpha behavior.

If present, `alpha` MUST be a closed object using one of the variants below.

Supported modes are exactly:

```text
opaque
mask
blend
```

Material 1.1 defines no separate alpha texture map.

Sampled source alpha comes from the base-color map's alpha channel when present; otherwise it is `1`.

## 19.1. Opaque mode

Opaque alpha is represented as:

```json
"alpha": {
  "mode": "opaque"
}
```

The object MUST contain exactly `mode`.

Source texture alpha is ignored for visibility.

The effective surface opacity is `1`.

Omitting `alpha` is equivalent to opaque mode.

## 19.2. Mask mode

Masked alpha is represented as:

```json
"alpha": {
  "mode": "mask",
  "opacity": 1,
  "cutoff": 0.5
}
```

Properties:

| Property | Type | Required | Meaning |
|---|---|---:|---|
| `mode` | `"mask"` | yes | masked/cutout alpha |
| `opacity` | number | no | constant alpha multiplier |
| `cutoff` | number | yes | visibility threshold |

`opacity` MUST be finite and in `[0, 1]`.

If omitted:

```text
opacity = 1
```

`cutoff` MUST be finite and in `[0, 1]`.

Conceptually:

```text
effectiveAlpha = sampledSourceAlpha × opacity
```

A fragment with:

```text
effectiveAlpha < cutoff
```

is discarded.

A fragment with:

```text
effectiveAlpha >= cutoff
```

is retained.

## 19.3. Blend mode

Blended alpha is represented as:

```json
"alpha": {
  "mode": "blend",
  "opacity": 0.8
}
```

Properties:

| Property | Type | Required | Meaning |
|---|---|---:|---|
| `mode` | `"blend"` | yes | ordinary alpha blending |
| `opacity` | number | no | constant alpha multiplier |

`opacity` MUST be finite and in `[0, 1]`.

If omitted:

```text
opacity = 1
```

Conceptually:

```text
effectiveAlpha = sampledSourceAlpha × opacity
```

The renderer adapter uses that effective alpha for ordinary blended transparency.

Renderer-specific sorting, depth-write configuration, and GPU blending constants remain renderer implementation details.

---

# 20. Defaults and normalized interpretation

A Material 1.1 consumer MUST interpret omitted optional scalar/alpha values using these defaults:

```text
baseColor = [1, 1, 1]
roughness = 1
metalness = 0
alpha = opaque
mask.opacity = 1
blend.opacity = 1
```

Additionally, when `maps.ambientOcclusion` is present and `ambientOcclusionStrength` is omitted:

```text
ambientOcclusionStrength = 1
```

There is no ambient-occlusion strength state when no ambient-occlusion map exists.

There is no default:

- material `name`;
- `mapping.widthCm`;
- `mapping.heightCm`;
- mask `cutoff`;
- texture resource path.

Required values MUST NOT be guessed.

Implementations MAY expose a normalized trusted in-memory representation that materializes applicable defaults explicitly.

Normal loading MUST NOT rewrite the durable JSON file merely to insert omitted defaults.

---

# 21. Design integration and material resolution

A Design 1.0 finish assignment contains:

```json
{
  "target": "floor",
  "material": "assets/materials/oak-natural/material.json"
}
```

When an application chooses to resolve that assignment through Material Format 1.1:

1. the design descriptor must already be Design 1.0-format conformant;
2. the design must already be architecture-resolved for its bound Apartment SVG;
3. the exact referenced material path is treated as the candidate Material 1.1 descriptor identity;
4. the material descriptor is parsed and validated according to this specification;
5. referenced textures are project-resolved and texture-resolved;
6. the resolved material may then be adapted to the renderer-independent/runtime PBR contract used by the application.

Material lookup MUST NOT search by:

- `name`;
- filename similarity;
- directory similarity;
- another material with similar maps;
- another material referenced elsewhere.

The design's exact project-relative material path is authoritative for the assignment.

## 21.1. No implicit repair

If material resolution fails, PlanAxis MUST NOT silently:

- substitute another material;
- search for a similarly named descriptor;
- drop one broken texture while pretending the complete material resolved;
- rewrite the design reference;
- rewrite the material descriptor;
- reinterpret a reference photograph as a normalized material asset.

Correction requires an explicit user/developer operation.

## 21.2. Atomic design-material application

Material Format itself does not mandate a browser UI or rendering lifecycle.

A consuming application MAY require all materials referenced by a selected design to resolve successfully before applying persistent finish assignments.

When such an all-or-nothing application policy is used, a material failure SHOULD remain distinguishable from architecture/design failure and SHOULD leave the underlying architecture inspectable with a safe neutral/default appearance.

---

# 22. Portability and filesystem boundary

Material descriptors and texture references are durable project data.

Persistent references MUST remain project-relative and portable.

Material loading MUST NOT introduce:

- absolute host filesystem paths;
- arbitrary filesystem traversal;
- symbolic-link traversal prohibited by Project Format;
- generic browser access to the project root.

Server-backed applications MUST resolve material resources through the centralized project-filesystem boundary or an equivalent implementation of the same normative Project Format rules.

---

# 23. Read and write behavior

Opening, validating, resolving, or rendering a Material 1.1 descriptor MUST NOT silently rewrite it.

Creation, import, normalization, migration, replacement, or deletion of durable material resources requires an explicit operation.

When PlanAxis writes or replaces a material descriptor in a future material-editing workflow, it SHOULD use an atomic replacement strategy where the host filesystem permits it.

Material Format 1.1 defines no requirement for:

- material discovery APIs;
- material creation UI;
- material editing UI;
- material deletion UI;
- material catalog indexing.

A valid application may initially rely on manually authored descriptors and manually placed texture resources.

---

# 24. Renderer independence

Material 1.1 expresses PBR domain intent using renderer-independent concepts.

A descriptor MUST NOT serialize:

- Three.js classes;
- Three.js enum values;
- WebGL/WebGPU handles;
- GPU resources;
- in-process texture symbols;
- renderer material instances;
- decoded image objects;
- renderer color-space constants;
- renderer UV-channel numbers;
- backend-specific blend/depth constants.

A renderer adapter is responsible for translating validated material semantics into its own runtime representation.

For ambient occlusion, the adapter is responsible for applying the red-channel non-color map and the effective strength defined by this specification using backend-appropriate material or shader facilities.

The persisted format is not defined by the current `RuntimePbrMaterial` TypeScript interface, even when an implementation maps Material 1.1 into that interface.

---

# 25. Numeric semantics

Material Format 1.1 is not an authoritative apartment geometry format.

JSON numbers in Material 1.1 use ordinary JSON numeric semantics.

Validators operating on already-parsed JavaScript values MUST reject non-finite values such as `NaN`, positive infinity, or negative infinity even though such values cannot occur in conforming JSON text.

The exact-decimal arithmetic requirements of Apartment SVG apply to authoritative architectural geometry, not to Material 1.1 color factors, PBR factors, ambient-occlusion strength, opacity values, or physical texture-repeat metadata.

---

# 26. Versioning and future evolution

## 26.1. Independent versioning

Material Format versions evolve independently from:

- Project Format;
- Apartment SVG;
- Design Format;
- model-asset formats;
- application versions.

## 26.2. Unsupported versions

An implementation that does not support the descriptor's `schema` value MUST reject Material Format interpretation.

It MUST NOT guess the meaning of an unsupported version.

Support for Material 1.0 does not imply support for Material 1.1, and support for Material 1.1 does not require silently interpreting a Material 1.0 document as Version 1.1.

An implementation MAY explicitly support both schemas.

## 26.3. Version 1.1 change from Version 1.0

Material 1.1 adds exactly these persistent capabilities relative to Material 1.0:

- optional `maps.ambientOcclusion`;
- optional `ambientOcclusionStrength`, permitted only when the ambient-occlusion map exists.

Material 1.1 otherwise preserves the Material 1.0 model and boundaries.

## 26.4. Future properties

Because Material 1.1 is recursively closed, future capabilities such as:

- additional texture maps;
- displacement or height maps;
- richer BRDF properties;
- material categories/tags;
- manufacturer metadata;
- procedural materials;
- per-material texture transforms;
- multiple persistent UV sets;

require an explicit later version or another accepted versioned contract.

## 26.5. Assignment-level orientation

Material 1.1 deliberately defines no orientation property.

A future design-format revision may add finish-assignment mapping overrides such as rotation when a concrete requirement justifies them.

Such state belongs to the assignment because the same reusable material may require different orientations on different surfaces.

# 27. Normative examples

## 27.1. Minimal scalar material

```json
{
  "schema": "planaxis-material/1.1",
  "name": "Default matte material"
}
```

Effective values:

```text
baseColor = [1, 1, 1]
roughness = 1
metalness = 0
alpha = opaque
```

No ambient-occlusion state exists because no ambient-occlusion map exists.

## 27.2. Scalar painted wall

```json
{
  "schema": "planaxis-material/1.1",
  "name": "Warm white paint",
  "baseColor": [0.88, 0.84, 0.76],
  "roughness": 0.82
}
```

No `mapping` is present because there are no texture maps.

## 27.3. Textured natural oak with ambient occlusion

```json
{
  "schema": "planaxis-material/1.1",
  "name": "Natural oak",
  "baseColor": [1, 1, 1],

    "ambientOcclusion": "assets/materials/oak-natural/ambient-occlusion.webp"
```

The ambient-occlusion map is sampled from red and applied at strength `0.8`.

# 28. Non-conforming examples

## 28.1. Descriptor outside `assets/materials/`

Descriptor path:

```text
references/materials/oak/material.json
```

Invalid because a Material 1.1 descriptor must be under `assets/materials/`.

## 28.2. Uppercase descriptor extension

Descriptor path:

```text
assets/materials/oak/material.JSON
```

Invalid because the descriptor extension must be lowercase `.json`.

## 28.3. Descriptor-relative texture path

```json
{
  "schema": "planaxis-material/1.1",
  "name": "Oak",
  "mapping": {
    "widthCm": 120,
    "heightCm": 20
  },
  "maps": {
    "baseColor": "base-color.webp"
  }
}
```

Invalid because texture references must be canonical project-relative paths under `assets/materials/`.

## 28.4. Maps without mapping

```json
{
  "schema": "planaxis-material/1.1",
  "name": "Oak",
  "maps": {
    "ambientOcclusion": "assets/materials/oak/ambient-occlusion.webp"
  }
}
```

Invalid because `mapping` is required whenever `maps` is present.

## 28.5. Mapping without maps

```json
{
  "schema": "planaxis-material/1.1",
  "name": "Paint",
  "mapping": {
    "widthCm": 100,
    "heightCm": 100
  }
}
```

Invalid because `mapping` must be absent when there are no texture maps.

## 28.6. Unsupported texture format

```json
{
  "schema": "planaxis-material/1.1",
  "name": "Stone",
  "mapping": {
    "widthCm": 80,
    "heightCm": 80
  },
  "maps": {
    "ambientOcclusion": "assets/materials/stone/ambient-occlusion.avif"
  }
}
```

Invalid because AVIF is not supported by Material Format 1.1.

## 28.7. Invalid scalar range

```json
{
  "schema": "planaxis-material/1.1",
  "name": "Invalid material",
  "ambientOcclusionStrength": 1.2,
  "mapping": {
    "widthCm": 80,
    "heightCm": 80
  },
  "maps": {
    "ambientOcclusion": "assets/materials/stone/ambient-occlusion.png"
  }
}
```

Invalid because ambient-occlusion strength must be in `[0, 1]`.

## 28.8. Ambient-occlusion strength without map

```json
{
  "schema": "planaxis-material/1.1",
  "name": "Invalid AO material",
  "ambientOcclusionStrength": 0.5
}
```

Invalid because `ambientOcclusionStrength` is permitted only when `maps.ambientOcclusion` exists.

## 28.9. Unknown property

```json
{
  "schema": "planaxis-material/1.1",
  "name": "Oak",
  "heightMap": "assets/materials/oak/height.png"
}
```

Invalid because Material 1.1 is closed and does not define height or displacement maps.

# 29. Conformance summary

A PlanAxis Material Format 1.1 implementation MUST at minimum enforce:

1. the supported `planaxis-material/1.1` schema identifier;
2. descriptor identity by project-relative path under `assets/materials/` with lowercase `.json`;
3. required non-empty human-readable `name`;
4. recursively closed JSON structures;
5. optional `baseColor` with exactly three finite `[0, 1]` sRGB components and default `[1, 1, 1]`;
6. optional finite `[0, 1]` `roughness` with default `1`;
7. optional finite `[0, 1]` `metalness` with default `0`;
8. optional finite `[0, 1]` `ambientOcclusionStrength`, permitted only when `maps.ambientOcclusion` exists and defaulting to `1` when that map exists and strength is omitted;
9. optional non-empty `maps` containing only base-color, roughness, metalness, normal, and ambient-occlusion references;
10. `mapping` required exactly when `maps` exists;
11. positive finite `mapping.widthCm` and `mapping.heightCm`;
12. canonical project-relative texture paths under `assets/materials/`;
13. exactly PNG, JPEG, and WebP texture formats using lowercase `.png`, `.jpg`, `.jpeg`, and `.webp`;
14. common physical period and orientation for all maps, including ambient occlusion;
15. base-color map as sRGB color data;
16. roughness from the green channel;
17. metalness from the blue channel;
18. tangent-space normal maps with `+X = +U`, `+Y = +V`, and `+Z = outward normal`;
19. ambient occlusion from the red channel as non-color data;
20. ambient-occlusion strength semantics using linear interpolation between unoccluded value `1` and the sampled AO value;
21. ambient occlusion affecting ambient/indirect illumination rather than geometry, direct-light visibility, or explicit cast shadows;
22. support for shared packed texture resources, including ORM channel reuse;
23. no persistent texture rotation, mirroring, offset, UV-channel selection, or other transform;
24. optional opaque/mask/blend alpha semantics as defined in section 19;
25. separation between Material Format conformance, project resolution, texture decoding, and renderer adaptation;
26. renderer-independent persistence with no Three.js/GPU/runtime objects;
27. no implicit material substitution, search-by-name repair, or silent descriptor rewriting;
28. preservation of PlanAxis Project Format path, portability, containment, and symbolic-link rules.

Material Format 1.1 defines a deliberately small reusable PBR material contract suitable for project-local home-design visualization while adding conventional ambient-occlusion support without introducing displacement, renderer-specific state, or architectural geometry semantics.

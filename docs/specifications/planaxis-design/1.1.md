# PlanAxis Design Format Specification

**Version:** 1.1  
**Status:** Normative specification  
**Language:** English  
**Schema identifier:** `planaxis-design/1.1`

---

# 1. Purpose and scope

This document defines **PlanAxis Design Format 1.1**, the persistent renderer-independent format used to describe an interior-design scenario within a PlanAxis project.

A design scenario records design intent associated with exactly one Apartment SVG architectural alternative.

Version 1.1 supports persistent design data for:

- surface-finish assignments;
- presentation overrides for tone mapping and exposure;
- explicitly placed artificial-light luminaires.

The format deliberately separates:

```text
architectural truth
    from
interior-design decisions
    from
runtime simulation state
    from
renderer implementation state
```

Apartment SVG remains the canonical source of architectural geometry and semantics. A PlanAxis design descriptor does not duplicate, replace, override, or repair architectural geometry.

A Design 1.1 luminaire represents **persistent lighting-design intent**. It describes an idealized light emitter independently of a rendering engine and independently of any future decorative 3D fixture asset.

PlanAxis Design Format 1.1 does **not** define:

- material descriptor internals;
- texture maps or physical material properties;
- 3D model assets or object placement;
- decorative fixture geometry;
- IES or other photometric profile resources;
- RGB / RGBW / colored-light semantics;
- daylight date, time, weather, or other runtime simulation state;
- environment assets or environment-lighting configuration;
- camera navigation or saved-view state;
- lens or aspect-ratio settings;
- shadow-map settings;
- renderer-specific light classes, intensity units, decay values, or GPU resources;
- post-processing;
- AI-generation instructions;
- scenario inheritance;
- a persistent active-design selection.

Those concerns require separate specifications, later versions, or runtime-only state when their semantics are concrete.

# 2. Normative keywords

The key words **REQUIRED / MUST**, **MUST NOT**, **SHOULD**, **SHOULD NOT**, **MAY**, and **OPTIONAL** are normative.

- **REQUIRED / MUST** — mandatory for conformance.
- **MUST NOT** — prohibited.
- **SHOULD** — recommended unless a documented reason justifies deviation.
- **SHOULD NOT** — discouraged unless a documented reason justifies deviation.
- **MAY / OPTIONAL** — permitted but not required.

If an example conflicts with a normative rule, the normative rule takes precedence.

# 3. Relationship to other PlanAxis formats

PlanAxis Design Format is versioned independently from:

- PlanAxis Project Format;
- Apartment SVG;
- PlanAxis Material Format;
- future PlanAxis model-asset formats;
- future photometric-resource formats;
- the PlanAxis application version.

A project may therefore combine versions independently, for example:

```text
PlanAxis Project Format 1.0
Apartment SVG 2.2
PlanAxis Design Format 1.1
PlanAxis Material Format 1.1
```

## 3.1. Relationship to Design Format 1.0

Design Format 1.1 is an additive evolution of Design Format 1.0.

The following Design 1.0 concepts retain the same meaning in 1.1:

- descriptor location and identity;
- `name`;
- strict `architecture` binding;
- `finishes`;
- finish-target identifiers;
- material references;
- `presentation`;
- project-relative path rules;
- recursively closed schema semantics;
- persistence and active-design behavior.

Version 1.1 adds:

```text
luminaires
```

and the nested luminaire vocabulary defined by this specification.

A Design 1.0 descriptor remains a Design 1.0 descriptor because its `schema` value remains:

```text
planaxis-design/1.0
```

An implementation MUST NOT silently reinterpret or rewrite a Design 1.0 descriptor as Design 1.1 merely because its existing fields are compatible.

Explicit migration from 1.0 to 1.1 MAY preserve all existing 1.0 fields unchanged and replace the schema identifier with:

```text
planaxis-design/1.1
```

provided the resulting document conforms to this specification.

## 3.2. PlanAxis Project Format

A design descriptor exists inside a filesystem-backed PlanAxis project and uses the project-relative path and filesystem-boundary rules defined by the applicable PlanAxis Project Format specification.

PlanAxis Project Format 1.0 reserves:

```text
designs/
```

for durable design-scenario data and:

```text
assets/materials/
```

for normalized material resources.

This specification gives design descriptors concrete semantics without changing the root project manifest.

Luminaires defined by Design 1.1 are self-contained design data and introduce no new project-resource directory.

## 3.3. Apartment SVG

Apartment SVG remains the source of architectural and geometric truth.

The design descriptor references one Apartment SVG architecture but MUST NOT duplicate architectural facts such as:

- walls;
- spaces;
- openings;
- architectural utilities;
- dimensions;
- floor or ceiling geometry;
- finish-target geometry.

Finish assignments address architectural surfaces through stable finish-target identifiers derived from the referenced architecture.

Luminaire placement uses the bound architecture's PlanAxis model coordinate system, but luminaires are design objects rather than Apartment SVG architectural elements.

In particular, Apartment SVG `ceiling-light` utility markers and Design 1.1 luminaires are distinct concepts.

An Apartment SVG ceiling-light marker:

- remains architectural/semantic source information;
- MUST NOT automatically become a Design 1.1 luminaire;
- MUST NOT implicitly bind to a Design 1.1 luminaire;
- does not supply luminous flux, color temperature, beam, dimming, or other luminaire semantics.

An application MAY offer an explicit user operation that creates a Design 1.1 luminaire using an Apartment SVG utility as a placement hint. The resulting luminaire MUST still be represented explicitly in the design descriptor and MUST NOT depend on an implicit runtime relationship.

## 3.4. PlanAxis Material Format

A `material` reference in Design Format 1.1 identifies a project-local resource location under `assets/materials/`.

Design Format 1.1 assigns no internal material semantics to the referenced resource. Material descriptor semantics are independently defined by supported PlanAxis Material Format versions.

Design-format conformance does not require a referenced material to exist or to conform to a particular material schema. Material resolution remains a separate concern.

## 3.5. Future model-asset formats

Design 1.1 luminaires describe light-emitting behavior only.

They do not contain:

- GLB/glTF references;
- fixture mesh references;
- transform references to future placed objects;
- product identifiers;
- physical housing geometry.

A later accepted contract may associate a luminaire with a placed fixture asset without changing the meaning of the Design 1.1 light-emitter semantics.

## 3.6. Future photometric formats

Design 1.1 does not define IES or another photometric-distribution resource.

The four luminaire types in this specification provide deliberately simple idealized emission semantics suitable before such a resource contract exists.

A later Design Format version may add an explicit photometric profile reference.

# 4. Conformance and resolution levels

A design descriptor is examined at distinct levels.

## 4.1. JSON-conformant

The file contains syntactically valid JSON representing exactly one JSON object.

## 4.2. Design-format conformant

The JSON object satisfies all structural and lexical rules of `planaxis-design/1.1`, including:

- supported schema identifier;
- recursively closed object structures;
- required properties;
- project-relative path syntax;
- finish-target identifier syntax;
- finish-assignment uniqueness;
- presentation value constraints;
- luminaire identifier uniqueness;
- luminaire type discrimination;
- luminaire numeric and orientation constraints.

Design-format conformance does not by itself prove that the referenced architecture or material resources exist.

## 4.3. Project-resolved

A design descriptor is project-resolved when its referenced architecture:

- resolves through the project filesystem boundary;
- is an accessible regular lowercase `.svg` file under `architecture/`;
- is reached without prohibited symbolic-link traversal;
- remains within the canonical project root.

Material-resource existence remains separate from Design 1.1 project resolution.

Luminaires introduce no external project-resource reference and therefore add no project-filesystem resolution step.

## 4.4. Architecture-resolved

A project-resolved design descriptor is architecture-resolved when:

1. the referenced Apartment SVG passes its own complete validation pipeline;
2. its renderer-independent architectural surfaces and finish targets can be derived;
3. every persisted finish target in the design exists in that derived target set.

A descriptor may remain design-format conformant while failing project or architecture resolution.

Luminaire coordinates are interpreted in the coordinate system of the bound architecture, but Design 1.1 does not require luminaire containment, collision, or attachment validation for architecture resolution.

## 4.5. Material-resolved

Material resolution is not defined by Design Format 1.1.

A syntactically valid material reference may identify a resource that does not yet exist or whose contents are not interpretable by a consuming application. Such a condition does not make the design descriptor structurally non-conformant.

## 4.6. No luminaire-resource resolution stage

A Design 1.1 luminaire is self-contained.

Because Design 1.1 defines no fixture-asset or photometric-resource references, there is no separate luminaire-resource resolution level in this version.

# 5. Terminology

## 5.1. Design descriptor

A **design descriptor** is a JSON file under `designs/` that conforms to this specification.

## 5.2. Design scenario

A **design scenario** is the persistent design intent represented by one design descriptor.

## 5.3. Design identity

The project-relative path of the design descriptor is its durable identity within the project.

No separate internal design ID exists in Version 1.1.

## 5.4. Design name

The `name` field is a human-readable display label only.

It is not:

- an identifier;
- a filesystem name;
- a uniqueness key;
- a reference target.

## 5.5. Architecture binding

The `architecture` field binds the design scenario to exactly one Apartment SVG document identified by project-relative path.

## 5.6. Finish target

A **finish target** is a stable renderer-independent semantic address for a designable architectural surface or scoped surface coverage derived from the referenced architecture.

## 5.7. Material reference

A **material reference** is a project-relative path under `assets/materials/`.

It identifies a resource location. It does not imply an internal material representation.

## 5.8. Luminaire

A **luminaire** is a persistent renderer-independent light-emitter definition owned by one design scenario.

In Design 1.1, a luminaire describes:

- stable identity within the design;
- idealized emitter type;
- placement;
- orientation where applicable;
- nominal luminous flux;
- correlated color temperature;
- enabled state;
- dimming;
- type-specific beam or emitter dimensions.

A Design 1.1 luminaire does not itself represent decorative fixture geometry.

## 5.9. Luminaire identity

The `id` property of a luminaire is its stable identity within the containing design descriptor.

Luminaire IDs:

- MUST be unique within one descriptor;
- are not project-global identifiers;
- are not Apartment SVG element IDs;
- do not imply a relationship to an Apartment SVG utility with the same spelling;
- remain the same identity regardless of array position.

## 5.10. Nominal luminous flux

`luminousFluxLumens` is the luminaire's nominal full-output luminous flux in lumens.

It is design intent, not a renderer-native intensity constant.

## 5.11. Effective luminous flux

The effective luminous flux of a luminaire is:

```text
enabled
    ? luminousFluxLumens * dimming
    : 0
```

This value remains a renderer-independent semantic quantity.

## 5.12. Color temperature

`colorTemperatureKelvin` is the intended correlated color temperature of the emitted white light in Kelvin.

Design 1.1 defines no RGB or arbitrary colored-light value.

# 6. Design descriptor location, identity, and encoding

## 6.1. Location

A design descriptor MUST be stored at a project-relative path under:

```text
designs/
```

The filename MUST use the lowercase `.json` extension.

Examples:

```text
designs/warm-modern.json
designs/scandinavian.json
designs/concepts/warm-modern.json
designs/alternatives/kitchen-dark.json
```

No additional filename or directory convention is required by Version 1.1.

## 6.2. Identity

The descriptor's complete project-relative path is its identity.

For example:

```text
designs/warm-modern.json
```

and:

```text
designs/archive/warm-modern.json
```

identify different design scenarios even if their contents are otherwise identical.

Moving or renaming a design descriptor therefore changes its identity.

## 6.3. Encoding

The file MUST contain UTF-8 encoded JSON representing exactly one JSON object.

A byte-order mark SHOULD NOT be written.

---

# 7. Project-relative path rules

All persistent paths in a Design 1.1 descriptor MUST use the project-relative path syntax defined by the applicable PlanAxis Project Format specification.

A project-relative path MUST NOT:

- be empty;
- begin with `/`;
- contain `\`;
- contain an empty path segment;
- contain a `.` path segment;
- contain a `..` path segment;
- contain a NUL character;
- contain a URI scheme such as `file:`;
- contain a Windows drive prefix such as `C:`;
- otherwise represent or resolve as an absolute filesystem path.

Persistent paths use `/` as the separator on every operating system.

---

# 8. Closed-schema rule

PlanAxis Design Format 1.1 is recursively closed.

Unknown properties are PROHIBITED:

- at the root object;
- inside each finish assignment;
- inside the `presentation` object;
- inside each luminaire;
- inside every luminaire `position`;
- inside every luminaire `orientation`.

Version 1.1 defines no `x-*`, `data-x-*`, or other extension-property mechanism.

A future format version may add properties explicitly.

---

# 9. Root object

The root JSON object supports exactly these properties:

| Property | Type | Required | Meaning |
|---|---|---:|---|
| `schema` | string | yes | schema identifier |
| `name` | string | yes | human-readable display name |
| `architecture` | string | yes | strict project-relative architecture binding |
| `finishes` | array | no | persistent finish assignments |
| `luminaires` | array | no | persistent artificial-light luminaires |
| `presentation` | object | no | persistent presentation overrides |

A representative document is:

```json
{
  "schema": "planaxis-design/1.1",
  "name": "Warm modern",
  "architecture": "architecture/concept-alt-2/apartment.svg",
  "finishes": [
    {
      "target": "floor",
      "material": "assets/materials/oak-natural/material.json"
    }
  ],
  "luminaires": [
    {
      "id": "living-pendant",
      "type": "point",
      "position": {
        "x": 420,
        "y": 315,
        "z": 245
      },
      "luminousFluxLumens": 1200,
      "colorTemperatureKelvin": 2700,
      "enabled": true,
      "dimming": 0.8
    }
  ],
  "presentation": {
    "toneMapping": "agx",
    "exposureEv": 0.7
  }
}
```

The minimum conforming root object contains only the three required properties:

```json
{
  "schema": "planaxis-design/1.1",
  "name": "Empty concept",
  "architecture": "architecture/apartment.svg"
}
```

---

# 10. `schema`

`schema` is REQUIRED.

Its value MUST be exactly:

```text
planaxis-design/1.1
```

An implementation that does not support the schema identifier MUST reject Design Format interpretation and MUST NOT guess the semantics of the document.

---

# 11. `name`

`name` is REQUIRED.

Its value MUST be a JSON string containing at least one non-whitespace Unicode character after trimming.

The stored value is the human-readable scenario name.

The `name`:

- MAY be duplicated by another design descriptor;
- MAY differ from the descriptor filename;
- MUST NOT be used as persistent identity.

---

# 12. `architecture`

`architecture` is REQUIRED.

Its value MUST be a project-relative path that:

- uses the path syntax defined in section 7;
- begins with `architecture/`;
- names a file using the lowercase `.svg` extension.

Example:

```json
"architecture": "architecture/concept-alt-2/apartment.svg"
```

The referenced architecture does not need to be the architecture currently selected by `architecture.active` in `planaxis.project.json`.

The project manifest's active-architecture selection and a design scenario's architecture binding are independent concepts.

## 12.1. Strict architecture binding

The architecture reference has strict semantics:

> The design scenario is defined for exactly the Apartment SVG identified by the `architecture` path.

A design MUST NOT be implicitly applied to another Apartment SVG merely because:

- the other document contains the same element IDs;
- the same finish-target IDs can be derived;
- the geometry appears similar;
- luminaire coordinates happen to fit;
- the files are related architectural alternatives.

Matching identifiers or coordinates are not sufficient evidence of design compatibility.

If a user wants to reuse a scenario with another architecture, that operation must be explicit and must produce or update a descriptor whose `architecture` property identifies the new architecture.

Version 1.1 does not define a dedicated copy, duplicate, or rebind operation.

## 12.2. Architecture existence and validation

Design-format conformance checks only the lexical/path rules above.

For project and architecture resolution, PlanAxis MUST additionally require that the referenced architecture:

1. resolves through the project filesystem boundary;
2. identifies an accessible regular `.svg` file;
3. remains under the canonical project root without prohibited symbolic-link traversal;
4. passes the complete Apartment SVG validation pipeline before architecture-dependent design resolution occurs.

If the architecture is missing, inaccessible, invalid, renamed, or otherwise unresolved, the design remains potentially Design 1.1-format conformant but cannot be architecture-resolved or applied as a resolved scenario.

---

# 13. `finishes`

`finishes` is OPTIONAL.

If present:

- it MUST be a JSON array;
- it MUST contain at least one assignment;
- every array item MUST conform to section 13.1;
- no two assignments may use the same `target` value.

An empty array is PROHIBITED.

If there are no finish assignments, the `finishes` property SHOULD be omitted.

## 13.1. Finish assignment object

Each finish assignment is a closed JSON object with exactly these properties:

| Property | Type | Required | Meaning |
|---|---|---:|---|
| `target` | string | yes | finish-target identifier |
| `material` | string | yes | project-relative material resource reference |

Example:

```json
{
  "target": "space:living-room:wall:wall-west:side-positive",
  "material": "assets/materials/paint-warm-white/material.json"
}
```

Unknown properties are PROHIBITED.

## 13.2. Duplicate target assignments

Within one `finishes` array, each `target` value MUST appear at most once.

Version 1.1 defines no precedence rule such as "first wins" or "last wins".

---

# 14. Finish-target identifiers

A `target` value MUST conform to one of the lexical forms in this section.

Identifiers embedded inside a finish-target string are Apartment SVG semantic IDs and therefore use the Apartment SVG `Id` lexical form:

```text
[A-Za-z][A-Za-z0-9._-]*
```

Because `:` is not permitted inside an Apartment SVG `Id`, the separators in finish-target identifiers are unambiguous.

## 14.1. Base floor and ceiling

```text
floor
ceiling
```

## 14.2. Wall sides

```text
wall:<wall-id>:side-negative
wall:<wall-id>:side-positive
```

Examples:

```text
wall:wall-living-west:side-negative
wall:wall-living-west:side-positive
```

## 14.3. Opening reveals

```text
wall:<wall-id>:opening:<opening-id>:reveal-start
wall:<wall-id>:opening:<opening-id>:reveal-end
wall:<wall-id>:opening:<opening-id>:reveal-top
wall:<wall-id>:opening:<opening-id>:reveal-bottom
```

Only physically existing reveal targets may resolve successfully.

## 14.4. Space-scoped floor and ceiling targets

```text
space:<space-id>:floor
space:<space-id>:ceiling
```

## 14.5. Space-scoped wall-side targets

```text
space:<space-id>:wall:<wall-id>:side-negative
space:<space-id>:wall:<wall-id>:side-positive
```

## 14.6. Unsupported target forms

Version 1.1 does not define space-scoped opening-reveal targets.

For example:

```text
space:zone-living:wall:wall-living-west:opening:window-01:reveal-start
```

is invalid.

## 14.7. Lexical validity versus architectural existence

A syntactically valid `target` does not prove that the target exists in the bound architecture.

A stale or unresolved target is an architecture-resolution failure, not malformed JSON.

---

# 15. Material references

The `material` property of a finish assignment MUST be a project-relative path that:

- follows section 7;
- begins with `assets/materials/`;
- contains at least one path segment after `assets/materials/`.

Examples:

```text
assets/materials/oak-natural/material.json
assets/materials/paint/warm-white
assets/materials/tiles/bathroom/matte-stone.material
```

Design Format 1.1 intentionally does not require:

- a particular filename;
- a particular filename extension;
- the referenced resource to exist;
- the referenced resource to be a regular file;
- the referenced resource to conform to a particular material schema.

A reference outside `assets/materials/` is invalid Design 1.1 data.

---

# 16. `luminaires`

`luminaires` is OPTIONAL.

If present:

- it MUST be a JSON array;
- it MUST contain at least one luminaire;
- every array item MUST conform to exactly one luminaire type in this section;
- every luminaire `id` MUST be unique within the array.

An empty array is PROHIBITED.

If there are no persistent luminaires, the `luminaires` property SHOULD be omitted.

Array order does not define luminaire identity, rendering priority, or precedence.

## 16.1. Luminaire identifier

Every luminaire MUST have an `id`.

A luminaire ID MUST match:

```text
[A-Za-z][A-Za-z0-9._-]*
```

Examples:

```text
living-pendant
kitchen_spot_01
hall.linear
AreaLight2
```

The luminaire ID namespace belongs to the design descriptor.

The same textual value MAY also exist as:

- an Apartment SVG element ID;
- a finish-target embedded ID;
- a luminaire ID in another design.

Such textual equality creates no relationship.

Within one `luminaires` array, duplicate IDs are PROHIBITED.

## 16.2. Luminaire types

The permitted `type` values are exactly:

```text
point
spot
linear
area
```

These values are PlanAxis-owned renderer-independent vocabulary.

They MUST NOT be interpreted as serialized Three.js class names or backend-specific object types.

Each type has the exact closed object shape defined later in this section.

## 16.3. Common luminaire properties

Every luminaire type contains these common properties:

| Property | Type | Required | Meaning |
|---|---|---:|---|
| `id` | string | yes | stable design-local luminaire identifier |
| `type` | enum string | yes | `point`, `spot`, `linear`, or `area` |
| `position` | object | yes | emitter origin/center in PlanAxis model-space centimeters |
| `luminousFluxLumens` | positive finite number | yes | nominal full-output luminous flux |
| `colorTemperatureKelvin` | positive finite number | yes | emitted white-light correlated color temperature |
| `enabled` | boolean | yes | whether the luminaire contributes light |
| `dimming` | finite number | yes | output multiplier in `[0, 1]` |

Directional luminaire types additionally require `orientation`.

Type-specific properties are defined in sections 16.10–16.13.

## 16.4. `position`

`position` is a REQUIRED closed object containing exactly:

| Property | Type | Required |
|---|---|---:|
| `x` | finite number | yes |
| `y` | finite number | yes |
| `z` | finite number | yes |

All coordinates are expressed in **centimeters**.

The position uses PlanAxis **model-space** coordinates:

- `x` uses the Apartment SVG / PlanAxis model X axis;
- `y` uses the Apartment SVG / PlanAxis model Y axis;
- `z` uses the PlanAxis model Z axis, positive upward.

For an architecture whose Apartment SVG level-local height is `localZ`, the corresponding model-space Z follows the established architectural relationship:

```text
modelZ = metadata.level.baseZ + localZ
```

A Design 1.1 luminaire therefore stores model-space `z`, not level-local `z`.

Example:

```json
"position": {
  "x": 420,
  "y": 315,
  "z": 245
}
```

Design-format conformance does not require the position to be:

- inside the apartment footprint;
- below the ceiling;
- outside a wall;
- collision-free;
- attached to an architectural surface.

Applications MAY impose stronger editing constraints without changing the persistent format.

## 16.5. `orientation`

`orientation` is REQUIRED for:

```text
spot
linear
area
```

and PROHIBITED for:

```text
point
```

It is a closed object containing exactly:

| Property | Type | Required | Meaning |
|---|---|---:|---|
| `headingDegrees` | finite number | yes | horizontal heading |
| `pitchDegrees` | finite number | yes | elevation of emission direction |
| `rollDegrees` | finite number | yes | rotation around the emission axis |

Constraints:

```text
0 <= headingDegrees < 360
-90 <= pitchDegrees <= 90
0 <= rollDegrees < 360
```

### 16.5.1. Heading

Heading uses the same top-view convention as Apartment SVG cameras:

```text
0°   = +X
90°  = +Y
180° = -X
270° = -Y
```

### 16.5.2. Pitch

Pitch uses:

```text
0°   = horizontal
>0°  = points downward
<0°  = points upward
+90° = straight down
-90° = straight up
```

The inclusive vertical endpoints are required because architectural luminaires commonly point directly downward or upward.

### 16.5.3. Roll

Roll rotates the emitter's local transverse axes around its emission direction.

For a rotationally symmetric `spot` luminaire, roll does not change the idealized Design 1.1 beam shape, but it remains part of the uniform orientation contract.

For `linear` and `area` luminaires, roll determines the orientation of the emitter's physical line/rectangle around the emission direction.

## 16.6. Normative orientation frame

The orientation contract MUST be interpreted independently of renderer Euler-order conventions.

Let:

```text
h = headingDegrees in radians
p = pitchDegrees in radians
r = rollDegrees in radians
```

The unit emission direction is:

```text
forward = (
  cos(p) * cos(h),
  cos(p) * sin(h),
  -sin(p)
)
```

Before roll, define the transverse side axis:

```text
side = (
  -sin(h),
  cos(h),
  0
)
```

and the corresponding orthogonal vertical axis:

```text
vertical = forward × side
```

Apply roll around `forward`:

```text
rolledSide =
  side * cos(r) +
  vertical * sin(r)

rolledVertical =
  vertical * cos(r) -
  side * sin(r)
```

The resulting frame is:

```text
forward
rolledSide
rolledVertical
```

A renderer adapter MUST derive its backend-specific transform from this semantic frame rather than relying on an undocumented renderer Euler convention.

This definition remains valid for straight-up and straight-down emitters.

## 16.7. `luminousFluxLumens`

`luminousFluxLumens` is REQUIRED.

It MUST be a finite JSON number for which:

```text
luminousFluxLumens > 0
```

It represents the luminaire's nominal full-output luminous flux in **lumens**.

Examples:

```json
"luminousFluxLumens": 470
```

```json
"luminousFluxLumens": 1200
```

```json
"luminousFluxLumens": 4200
```

The value MUST NOT store:

- a Three.js intensity number;
- candela merely because a renderer API expects candela;
- exposure-compensated output;
- shadow strength;
- an arbitrary unitless brightness slider.

A rendering adapter is responsible for mapping the persistent PlanAxis luminaire semantics to physically meaningful backend parameters where supported.

## 16.8. `colorTemperatureKelvin`

`colorTemperatureKelvin` is REQUIRED.

It MUST be a finite JSON number for which:

```text
colorTemperatureKelvin > 0
```

It represents the intended correlated color temperature of emitted **white light** in Kelvin.

Examples:

```json
"colorTemperatureKelvin": 2200
```

```json
"colorTemperatureKelvin": 2700
```

```json
"colorTemperatureKelvin": 4000
```

```json
"colorTemperatureKelvin": 6500
```

Design 1.1 deliberately does not define:

- RGB color;
- RGBW channels;
- hue/saturation;
- gels;
- spectral power distributions.

A user interface MAY expose a practical editing range without changing the persistent format.

## 16.9. `enabled` and `dimming`

`enabled` is REQUIRED and MUST be a JSON boolean.

`dimming` is REQUIRED and MUST be a finite JSON number satisfying:

```text
0 <= dimming <= 1
```

The effective renderer-independent luminous flux is:

```text
enabled
    ? luminousFluxLumens * dimming
    : 0
```

Examples:

```json
"enabled": true,
"dimming": 1
```

```json
"enabled": true,
"dimming": 0.35
```

```json
"enabled": false,
"dimming": 0.8
```

An application MUST preserve the stored `dimming` value when `enabled` is `false`; disabling a luminaire does not rewrite its dimming setting to zero.

## 16.10. `point` luminaire

A `point` luminaire is an idealized omnidirectional point emitter.

Its object contains exactly:

| Property | Required |
|---|---:|
| `id` | yes |
| `type` = `point` | yes |
| `position` | yes |
| `luminousFluxLumens` | yes |
| `colorTemperatureKelvin` | yes |
| `enabled` | yes |
| `dimming` | yes |

`orientation` is PROHIBITED.

No beam-angle or physical-size property is defined.

Example:

```json
{
  "id": "living-pendant",
  "type": "point",
  "position": {
    "x": 420,
    "y": 315,
    "z": 245
  },
  "luminousFluxLumens": 1200,
  "colorTemperatureKelvin": 2700,
  "enabled": true,
  "dimming": 0.8
}
```

The idealized emission is rotationally symmetric over the full sphere.

## 16.11. `spot` luminaire

A `spot` luminaire is an idealized directional point emitter with a conical beam.

Its object contains exactly:

| Property | Required |
|---|---:|
| `id` | yes |
| `type` = `spot` | yes |
| `position` | yes |
| `orientation` | yes |
| `luminousFluxLumens` | yes |
| `colorTemperatureKelvin` | yes |
| `enabled` | yes |
| `dimming` | yes |
| `beamAngleDegrees` | yes |

`beamAngleDegrees` MUST be a finite JSON number satisfying:

```text
0 < beamAngleDegrees < 180
```

It represents the **full cone angle**, not the half-angle.

Example:

```json
{
  "id": "kitchen-spot-01",
  "type": "spot",
  "position": {
    "x": 610,
    "y": 215,
    "z": 260
  },
  "orientation": {
    "headingDegrees": 0,
    "pitchDegrees": 90,
    "rollDegrees": 0
  },
  "luminousFluxLumens": 700,
  "colorTemperatureKelvin": 3000,
  "enabled": true,
  "dimming": 1,
  "beamAngleDegrees": 36
}
```

Design 1.1 defines no persistent penumbra, field angle, edge softness, falloff exponent, or IES distribution.

A renderer MUST choose a reasonable implementation-specific falloff while preserving the declared beam angle and total-output intent as closely as practical.

## 16.12. `linear` luminaire

A `linear` luminaire is an idealized finite one-sided line emitter.

Its object contains exactly:

| Property | Required |
|---|---:|
| `id` | yes |
| `type` = `linear` | yes |
| `position` | yes |
| `orientation` | yes |
| `luminousFluxLumens` | yes |
| `colorTemperatureKelvin` | yes |
| `enabled` | yes |
| `dimming` | yes |
| `lengthCm` | yes |

`lengthCm` MUST be a finite JSON number satisfying:

```text
lengthCm > 0
```

The stored position is the center of the emitting line.

The line extends along `rolledSide` from the normative orientation frame.

Its endpoints are conceptually:

```text
position - rolledSide * (lengthCm / 2)
position + rolledSide * (lengthCm / 2)
```

The luminaire emits from one side only, centered around the `forward` direction.

Example:

```json
{
  "id": "kitchen-counter-linear",
  "type": "linear",
  "position": {
    "x": 540,
    "y": 180,
    "z": 220
  },
  "orientation": {
    "headingDegrees": 90,
    "pitchDegrees": 90,
    "rollDegrees": 0
  },
  "luminousFluxLumens": 1600,
  "colorTemperatureKelvin": 3000,
  "enabled": true,
  "dimming": 0.9,
  "lengthCm": 120
}
```

Design 1.1 does not define a line thickness or fixture housing cross-section.

## 16.13. `area` luminaire

An `area` luminaire is an idealized finite one-sided rectangular emitter.

Its object contains exactly:

| Property | Required |
|---|---:|
| `id` | yes |
| `type` = `area` | yes |
| `position` | yes |
| `orientation` | yes |
| `luminousFluxLumens` | yes |
| `colorTemperatureKelvin` | yes |
| `enabled` | yes |
| `dimming` | yes |
| `widthCm` | yes |
| `heightCm` | yes |

Both dimensions MUST be finite JSON numbers satisfying:

```text
widthCm > 0
heightCm > 0
```

The stored position is the center of the rectangle.

The rectangle's axes are:

```text
width  -> rolledSide
height -> rolledVertical
normal -> forward
```

The luminaire emits from the `forward` side only.

Example:

```json
{
  "id": "living-softbox",
  "type": "area",
  "position": {
    "x": 350,
    "y": 480,
    "z": 210
  },
  "orientation": {
    "headingDegrees": 270,
    "pitchDegrees": 15,
    "rollDegrees": 90
  },
  "luminousFluxLumens": 3000,
  "colorTemperatureKelvin": 4000,
  "enabled": true,
  "dimming": 0.6,
  "widthCm": 80,
  "heightCm": 40
}
```

Design 1.1 defines no emitter thickness, housing geometry, or two-sided area emission.

## 16.14. Type discrimination

The `type` property determines the exact permitted luminaire shape.

Properties belonging to another type are PROHIBITED.

For example:

- `orientation` is invalid on `point`;
- `beamAngleDegrees` is valid only on `spot`;
- `lengthCm` is valid only on `linear`;
- `widthCm` and `heightCm` are valid only on `area`.

A consumer MUST NOT ignore such extra properties and guess intent.

## 16.15. Luminaire ordering and identity

Luminaire identity comes from `id`, not array index.

Reordering `luminaires`:

- MUST NOT change luminaire identity;
- MUST NOT imply draw order;
- MUST NOT imply priority;
- MUST NOT change effective output.

An editor SHOULD preserve a stable order where practical to avoid unnecessary descriptor churn.

## 16.16. No implicit architectural attachment

Design 1.1 does not define:

- `wall`;
- `ceiling`;
- `space`;
- `utility`;
- `parent`;
- `attachment`;
- `host`;
- `target`;

as luminaire attachment/reference properties.

A luminaire's persisted placement is its explicit model-space position and, where applicable, orientation.

Moving architectural geometry does not automatically move a luminaire unless an explicit design-editing operation updates the luminaire data.

## 16.17. No fixture asset reference

A luminaire MUST NOT contain a project-relative 3D model reference in Design 1.1.

The light emitter and any future decorative fixture object remain separate concepts until a later accepted contract defines their relationship.

## 16.18. No IES or arbitrary photometric distribution

A luminaire MUST NOT contain fields such as:

```text
ies
iesProfile
photometricProfile
candelaDistribution
```

Design 1.1 intentionally uses simple type semantics.

A later format version may introduce a normalized photometric-resource reference.

## 16.19. No RGB light color

A luminaire MUST NOT contain arbitrary RGB/RGBA color fields.

Design 1.1 supports white light through:

```text
colorTemperatureKelvin
```

only.

# 17. `presentation`

`presentation` is OPTIONAL.

If present:

- it MUST be a JSON object;
- it MUST contain at least one supported property;
- it MUST contain no unknown properties.

An empty object is PROHIBITED.

If no persistent presentation override is required, the `presentation` property SHOULD be omitted.

Supported properties are:

| Property | Type | Required | Meaning |
|---|---|---:|---|
| `toneMapping` | enum string | no | PlanAxis presentation tone-mapping choice |
| `exposureEv` | finite JSON number | no | exposure compensation in EV |

At least one of them MUST be present whenever `presentation` exists.

## 17.1. `toneMapping`

Permitted values are exactly:

```text
agx
aces-filmic
neutral
```

These are PlanAxis-owned renderer-independent vocabulary values.

A rendering adapter maps them to its own backend implementation.

The descriptor MUST NOT persist rendering-library constants, enum numbers, class names, or other implementation-specific values.

If `toneMapping` is omitted, the consuming PlanAxis application uses its current presentation default.

The omission does not imply a persisted schema-level value.

## 17.2. `exposureEv`

`exposureEv` is a finite JSON number representing exposure compensation in photographic EV stops.

Design Format 1.1 intentionally does not restrict this value to the current browser UI range.

A user interface MAY expose a narrower editing range without changing the persistent format.

If `exposureEv` is omitted, the consuming PlanAxis application uses its current presentation default.

## 17.3. Presentation data not included in Version 1.1

The following are not Design 1.1 presentation properties:

- environment resource;
- environment intensity;
- environment rotation;
- daylight date or time;
- weather;
- Studio/Physical lighting-mode selection;
- camera selection;
- camera position or orientation;
- orbit/navigation state;
- Walk pose;
- focal length;
- aspect ratio;
- viewport size;
- post-processing settings.

Runtime daylight controls remain transient simulation state and are not persisted by Design 1.1.

# 18. Numeric semantics

PlanAxis Design Format is not an authoritative architecture-geometry format.

JSON numbers in Design 1.1 use ordinary JSON numeric semantics and may be represented as ordinary TypeScript/JavaScript `number` values after validation.

This includes:

- `exposureEv`;
- luminaire position;
- orientation angles;
- luminous flux;
- color temperature;
- dimming;
- beam angle;
- emitter dimensions.

All numeric values required to be finite MUST reject JSON values that cannot be represented as finite runtime numbers after parsing.

The exact-decimal arithmetic rules used for authoritative Apartment SVG geometry do not apply to Design 1.1 luminaire placement or presentation values.

Luminaire coordinates remain deliberate design placement data; they do not become authoritative architectural geometry merely because they use centimeters.

Design descriptors MUST NOT contain redundant architectural geometry merely to avoid resolving the referenced Apartment SVG.

# 19. Architecture resolution and stale references

After the bound Apartment SVG has passed its own validation pipeline, PlanAxis derives its renderer-independent architectural surfaces and finish targets.

Every persisted finish assignment MUST resolve against that exact derived target set before the design is considered architecture-resolved.

## 19.1. Stale finish target

A finish target may become stale when the referenced architecture changes, for example when:

- a wall is removed or renamed;
- an opening is removed or renamed;
- a space is removed or renamed;
- changed geometry causes a previously existing reveal or space-scoped target to no longer exist.

A stale target does not retroactively make the JSON malformed.

PlanAxis SHOULD report unresolved finish targets distinctly from:

- JSON syntax failures;
- Design 1.1 structural failures;
- project-filesystem failures;
- Apartment SVG validation failures.

## 19.2. Luminaire placement after architecture changes

A luminaire contains no architecture-element reference and therefore cannot become a stale reference in the same sense as a finish assignment.

However, editing the bound architecture may make a previously sensible luminaire placement physically inappropriate, for example:

- a ceiling height changes;
- a wall moves through a luminaire;
- a room layout changes around it.

Design 1.1 does not define automatic geometric repair for such cases.

Applications MAY provide diagnostics or editing assistance, but they MUST NOT silently rewrite luminaire coordinates during ordinary loading.

## 19.3. No implicit repair

PlanAxis MUST NOT silently repair an unresolved or awkward design state by:

- guessing a replacement wall, space, or opening;
- using a similarly named ID;
- selecting another architecture;
- dropping a finish assignment without reporting it;
- moving a luminaire to a nearby surface;
- snapping a luminaire to an Apartment SVG utility;
- changing luminaire type or output;
- rewriting the design descriptor during ordinary loading.

Correction requires an explicit design-editing operation.

---

# 20. Application and selection semantics

## 20.1. No persistent active design

PlanAxis Design Format 1.1 defines no project-level or design-level persistent "active design" property.

The PlanAxis Project Format 1.0 manifest remains unchanged and contains no active-design reference.

Which design scenario is currently selected is application/session state.

Selecting a scenario MUST NOT silently modify:

- `planaxis.project.json`;
- the referenced Apartment SVG;
- another design descriptor.

## 20.2. Applying a design

A design may be applied as a resolved scenario only to the exact architecture identified by its `architecture` property.

A consuming application may independently support:

- finish assignments;
- persistent presentation overrides;
- luminaire persistence;
- luminaire rendering;
- luminaire editing.

The format contract does not require every application version to render every supported design feature merely because the JSON is structurally valid. Unsupported schema versions, however, MUST still be rejected rather than guessed.

## 20.3. Runtime daylight state is independent

Persistent luminaires and runtime daylight simulation are separate concerns.

Design 1.1 does not persist:

- simulation instant;
- date;
- time;
- weather;
- physical daylight mode;
- Studio lighting mode.

Selecting, editing, or applying a Design 1.1 descriptor MUST NOT implicitly overwrite runtime daylight simulation state unless a future accepted contract explicitly defines such behavior.

---

# 21. Persistence and write behavior

Design descriptors are durable project data.

Creating or modifying a design descriptor is an explicit design-editing operation.

PlanAxis MUST NOT silently rewrite a design descriptor merely because it was opened, selected, validated, or rendered.

When PlanAxis writes or replaces a design descriptor, it SHOULD use an atomic replacement strategy where the host filesystem permits it so interruption does not leave a partially written durable descriptor.

Changing the `architecture` value is an explicit durable design change. It MUST NOT occur automatically because another architecture appears compatible.

Adding, moving, rotating, deleting, enabling, disabling, dimming, or otherwise editing a luminaire is an explicit durable design operation when the change is committed to the design scenario.

Runtime preview changes MAY remain transient until the user/application performs the explicit design write.

---

# 22. Versioning and future evolution

## 22.1. Independent versioning

Design Format versions evolve independently from Project Format, Apartment SVG, material formats, future asset/photometric formats, and application versions.

## 22.2. Unsupported versions

An implementation that does not support the descriptor's `schema` value MUST reject Design Format interpretation.

It MUST NOT guess the meaning of an unsupported version.

## 22.3. Design 1.0 compatibility

Design Format 1.0 remains a valid earlier version.

A PlanAxis implementation MAY support both:

```text
planaxis-design/1.0
planaxis-design/1.1
```

simultaneously.

Reading a Design 1.0 descriptor MUST NOT automatically persist a 1.1 migration.

A design must use schema 1.1 before it may persist `luminaires`.

## 22.4. Future properties

Because Design 1.1 is recursively closed, capabilities such as:

- 3D object placement;
- fixture model references;
- IES photometric profiles;
- RGB/RGBW lighting;
- lighting groups, circuits, scenes, or control systems;
- environment assets;
- richer presentation settings;
- saved render views;

require an explicit later version or another accepted versioned contract.

Version 1.1 intentionally does not reserve empty placeholder objects for future concepts.

## 22.5. Scenario inheritance

Version 1.1 defines no design-to-design inheritance, parent scenario, base scenario, or overlay mechanism.

Each descriptor is self-contained with respect to the design choices represented by this version.

# 25. Conformance summary

A JSON file conforms to PlanAxis Design Format 1.1 only if all applicable rules in this specification are satisfied.

At minimum:

1. the document is a JSON object;
2. `schema` is exactly `planaxis-design/1.1`;
3. `name` is a non-empty human-readable string;
4. `architecture` is a valid project-relative lowercase `.svg` path under `architecture/`;
5. the document contains no unknown root properties;
6. `finishes`, when present, is non-empty and contains unique valid finish targets;
7. every finish assignment is closed and contains a valid project-relative material reference under `assets/materials/`;
8. `presentation`, when present, is non-empty, recursively closed, and uses only supported values;
9. `luminaires`, when present, is non-empty;
10. every luminaire has a unique valid design-local `id`;
11. every luminaire uses exactly one supported type;
12. every luminaire is recursively closed and contains exactly the fields permitted by its type;
13. every position component is finite and expressed in model-space centimeters;
14. every oriented luminaire contains a valid heading/pitch/roll orientation;
15. every nominal luminous flux is finite and positive;
16. every color temperature is finite and positive;
17. every luminaire has an explicit boolean `enabled` value;
18. every `dimming` value is finite and within `[0, 1]`;
19. every spot beam angle is finite and strictly between `0` and `180` degrees;
20. every linear length is finite and positive;
21. every area width and height is finite and positive;
22. point luminaires contain no orientation;
23. no RGB light color, fixture model, IES profile, architectural attachment, renderer constant, or other unsupported property is persisted;
24. no persistent path violates the applicable project-relative path rules.

Project resolution, architecture resolution, material resolution, luminaire rendering, and physical lighting quality are separate from structural Design 1.1 conformance.

# 26. Final principle

PlanAxis Design Format 1.1 persists **design intent**, not renderer state.

For lighting, that means the durable scenario records concepts such as:

```text
this luminaire exists
at this model-space placement
with this idealized emitter type
with this nominal luminous output
with this white-light color temperature
with this beam or emitter size
and with this enabled/dimming state
```

It does not persist concepts such as:

```text
Three.js PointLight
shadow-map resolution
renderer intensity scalar
GPU resource
path-tracer object
runtime daylight time
weather
Studio/Physical mode
```

The renderer may evolve while the design contract remains stable.

Apartment SVG remains architectural truth. Design 1.1 luminaires remain explicit scenario-owned lighting decisions. Future fixture assets and photometric profiles may extend those decisions only through separately accepted, versioned contracts.

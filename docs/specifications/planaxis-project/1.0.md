# PlanAxis Project Format Specification

**Version:** 1.0  
**Status:** Normative specification  
**Language:** English  
**Schema identifier:** `planaxis-project/1.0`

---

# 1. Purpose and scope

This document defines the **PlanAxis Project Format 1.0**, the portable filesystem layout used
to contain one apartment-renovation project.

A PlanAxis project provides a stable top-level container for:

- one or more Apartment SVG architectural alternatives;
- normalized assets used by PlanAxis;
- source and reference material;
- design-scenario data;
- generated renders and AI presentation output;
- disposable PlanAxis internal data.

The project format defines project organization, path semantics, filesystem boundaries, and
the root project manifest.

It does **not** redefine Apartment SVG geometry or semantics. Each Apartment SVG document
remains governed independently by its own Apartment SVG specification.

This version intentionally does not define the internal schemas of future material assets,
3D-model assets, design scenarios, lighting setups, or AI workflow descriptors.

---

# 2. Normative keywords

The key words **REQUIRED / MUST**, **MUST NOT**, **SHOULD**, **SHOULD NOT**, **MAY**, and
**OPTIONAL** are normative.

- **REQUIRED / MUST** — mandatory for conformance.
- **MUST NOT** — prohibited.
- **SHOULD** — recommended unless a documented reason justifies deviation.
- **SHOULD NOT** — discouraged unless a documented reason justifies deviation.
- **MAY / OPTIONAL** — permitted but not required.

If an example conflicts with a normative rule, the normative rule takes precedence.

---

# 3. Terminology

## 3.1. Project root

The **project root** is the physical filesystem directory containing
`planaxis.project.json`.

The project root is the authorization and portability boundary for project-relative
resources.

## 3.2. Project manifest

The **project manifest** is the required root file:

```text
planaxis.project.json
```

It identifies the project-format version, provides the human-readable project name, and
selects the active Apartment SVG.

## 3.3. Project-relative path

A **project-relative path** is a canonical portable path interpreted relative to the project
root according to section 8.

A project-relative path is not an operating-system-native path and is never absolute.

## 3.4. Active architecture

The **active architecture** is the Apartment SVG document referenced by
`architecture.active` in the project manifest.

The active architecture is the apartment geometry currently selected for the project.

## 3.5. Durable project data

**Durable project data** is project information that must survive normal PlanAxis operation
and cache deletion.

The manifest and meaningful content under `architecture/`, `assets/`, `references/`,
`designs/`, and `outputs/` are durable unless a later format explicitly states otherwise.

## 3.6. Disposable internal data

**Disposable internal data** is derived implementation data stored under `.planaxis/`.

A conforming project must remain usable after the complete `.planaxis/` directory has been
deleted.

---

# 4. Project and Apartment SVG conformance are independent

PlanAxis Project Format conformance and Apartment SVG conformance are separate concerns.

A project may be structurally valid while its active Apartment SVG is invalid.

For example:

```text
project format: valid
active Apartment SVG: invalid
```

is a valid and openable PlanAxis project. The Apartment SVG validation pipeline must report
the Apartment SVG errors independently.

Project-format validation must not replace, duplicate, weaken, or silently repair Apartment
SVG validation.

Conversely, an individually valid Apartment SVG does not make its containing directory a
valid PlanAxis project.

---

# 5. Project root structure

## 5.1. Reserved names

The following names are reserved at the project root:

```text
planaxis.project.json
architecture/
assets/
references/
designs/
outputs/
.planaxis/
```

Reserved names are case-sensitive normative names and MUST use the spelling shown above.

A conforming project MUST NOT use a reserved name for a different purpose.

## 5.2. Required project contents

A conforming Project Format 1.0 project MUST contain:

```text
planaxis.project.json
architecture/
```

and the regular file referenced by `architecture.active`.

The active architecture file MUST be located under `architecture/`.

## 5.3. Optional reserved directories

The following reserved directories MAY be absent:

```text
assets/
references/
designs/
outputs/
.planaxis/
```

A PlanAxis project initializer SHOULD create the recommended complete directory structure,
but project validity does not depend on empty optional directories being present.

PlanAxis MAY create an optional reserved directory when it first needs that directory.

## 5.4. Additional files and directories

Unrecognized non-reserved files and directories MAY exist in the project root or below it.

For example, a project may contain:

```text
notes.md
measurements.xlsx
renovation-budget.pdf
.git/
```

Such files have no PlanAxis Project Format semantics unless another PlanAxis specification
explicitly assigns them semantics.

Their presence alone MUST NOT make an otherwise conforming project invalid.

---

# 6. Recommended directory layout

A newly initialized project SHOULD use this layout:

```text
my-apartment/
│
├── planaxis.project.json
├── architecture/
│   ├── existing.svg
│   └── variants/
├── assets/
│   ├── materials/
│   ├── models/
│   └── environments/
├── references/
│   ├── materials/
│   ├── products/
│   └── inspiration/
├── designs/
├── outputs/
│   ├── renders/
│   └── ai/
└── .planaxis/
    ├── cache/
    └── temp/
```

The project-root directory name itself has no PlanAxis semantics and MAY be renamed without
modifying the project manifest.

The subdirectories shown below reserved top-level directories are recommended organization
for Project Format 1.0. Their future descriptor schemas are not defined by this version.

---

# 7. Project manifest

## 7.1. Filename and encoding

The project manifest MUST be located directly under the project root and MUST be named:

```text
planaxis.project.json
```

The file MUST contain UTF-8 encoded JSON representing exactly one JSON object.

A byte-order mark SHOULD NOT be written.

## 7.2. Required structure

The Project Format 1.0 manifest has this structure:

```json
{
  "schema": "planaxis-project/1.0",
  "name": "My apartment renovation",
  "architecture": {
    "active": "architecture/existing.svg"
  }
}
```

The root object and the `architecture` object are closed schemas. Properties not defined by
this specification MUST NOT appear.

## 7.3. `schema`

`schema` is REQUIRED.

Its value MUST be exactly:

```text
planaxis-project/1.0
```

The project-format version is independent of the PlanAxis application version and the
Apartment SVG version.

## 7.4. `name`

`name` is REQUIRED.

Its value MUST be a JSON string containing at least one non-whitespace Unicode character
after trimming.

The value is a human-readable project name. It is not a filesystem name, persistent
identifier, or architectural identifier.

## 7.5. `architecture`

`architecture` is REQUIRED and MUST be a JSON object.

It MUST contain exactly one property in Project Format 1.0:

```text
active
```

## 7.6. `architecture.active`

`architecture.active` is REQUIRED and MUST be a project-relative path.

It MUST:

- use the project-relative path syntax in section 8;
- begin with `architecture/`;
- identify a regular file;
- identify a file with the lowercase `.svg` filename extension;
- resolve without traversing a symbolic link;
- resolve to a location within the canonical project root.

Project-format validation establishes only that the referenced file is an accessible
candidate Apartment SVG. Apartment SVG conformance is validated separately.

---

# 8. Project-relative path syntax

## 8.1. General form

Persistent PlanAxis references to project files MUST use project-relative paths.

Examples:

```text
architecture/existing.svg
architecture/variants/open-kitchen.svg
assets/models/dining-chair/model.glb
assets/materials/oak-natural/base-color.webp
```

Project-relative paths MUST use `/` as the path separator on every operating system.

The host operating system's native path representation may be used internally only after
the project-relative path has passed validation.

## 8.2. Prohibited forms

A project-relative path MUST NOT:

- be empty;
- begin with `/`;
- contain `\`;
- contain an empty path segment;
- contain a `.` path segment;
- contain a `..` path segment;
- contain a NUL character;
- contain a URI scheme such as `file:`;
- contain a Windows drive prefix such as `C:`;
- otherwise represent or resolve as an absolute filesystem path.

These rules apply before operating-system path resolution.

## 8.3. Persistent absolute paths

Persistent PlanAxis project data MUST NOT depend on absolute filesystem paths outside the
project root.

Machine-local absolute paths MAY exist transiently in process memory or disposable
`.planaxis/` data, but they MUST NOT be required to copy and open the durable project on
another supported system.

---

# 9. Filesystem boundary and symbolic links

## 9.1. Canonical project root

A PlanAxis implementation MUST establish one canonical physical project root before
resolving project resources.

The path supplied to locate the project root MAY itself pass through operating-system
indirection before the canonical root is established.

After the canonical root is established, project-resource resolution MUST remain confined
to that root.

## 9.2. Symbolic-link traversal

PlanAxis MUST NOT traverse symbolic links when resolving resources below the canonical
project root.

A project-relative resource path is invalid for PlanAxis access if the target or any
required path component below the canonical project root is a symbolic link.

This rule applies to both reads and writes.

## 9.3. Root containment

Every filesystem operation initiated from a project-relative path MUST verify that the
resolved target remains within the canonical project root.

String concatenation alone is not sufficient evidence of containment.

Project-consuming applications SHOULD centralize path validation, resolution, containment,
and symbolic-link policy in one project-filesystem boundary rather than reimplementing these
rules independently.

---

# 10. Directory semantics

## 10.1. `architecture/`

`architecture/` contains Apartment SVG documents representing architectural alternatives.

Each contained Apartment SVG remains an independent source of architectural and geometric
truth under the applicable Apartment SVG specification.

The project manifest selects the currently active document. The manifest MUST NOT duplicate
its geometry.

A recommended organization is:

```text
architecture/
├── existing.svg
└── variants/
    ├── open-kitchen.svg
    ├── larger-bathroom.svg
    └── moved-bedroom-door.svg
```

Project Format 1.0 does not define relationships, ancestry, or change history between
architectural alternatives.

## 10.2. `assets/`

`assets/` contains normalized resources intended for direct PlanAxis use.

Recommended categories are:

```text
assets/
├── materials/
├── models/
└── environments/
```

Examples include PBR material resources, GLB/glTF model assets, and environment maps.

Project Format 1.0 does not define material descriptors, model-asset descriptors, asset IDs,
texture-map requirements, or supported asset file formats beyond the project-container
semantics in this document.

Normalized assets SHOULD be self-contained enough that normal PlanAxis use does not depend
on the source material from which they were created.

Texture maps that belong to one material SHOULD normally be stored with that material
instead of in a global anonymous texture directory.

## 10.3. `references/`

`references/` contains source material used to understand, reproduce, select, or generate
design content.

Recommended categories are:

```text
references/
├── materials/
├── products/
└── inspiration/
```

Examples include:

- webshop product photographs;
- screenshots;
- material sample photographs;
- manufacturer imagery;
- inspiration images;
- photographs used as AI-generation input.

Reference files do not become normalized PlanAxis scene assets merely by existing under
`references/`.

User-provided filenames under `references/` MAY remain human-oriented and need not follow a
PlanAxis asset-ID convention.

## 10.4. `designs/`

`designs/` is reserved for durable design-scenario data.

Project Format 1.0 does not define:

- design descriptor filenames;
- design IDs;
- surface-finish assignments;
- furniture placement;
- lighting configuration;
- renderer presentation state;
- AI-generation instructions.

Those contracts require separate versioned specifications when introduced.

## 10.5. `outputs/`

`outputs/` contains generated artifacts that may be valuable to the user but are not
authoritative project inputs.

Recommended categories are:

```text
outputs/
├── renders/
└── ai/
```

`renders/` is intended for output produced directly by PlanAxis rendering workflows.

`ai/` is intended for AI-generated or AI-finished presentation output.

PlanAxis SHOULD preserve existing user-valued outputs unless replacement was explicitly
requested.

The durable project MUST NOT require an output file to reconstruct its architecture,
normalized assets, or design state. If an output becomes an intentional future input, it
SHOULD be explicitly copied or imported into an appropriate durable input location.

## 10.6. `.planaxis/`

`.planaxis/` is reserved exclusively for PlanAxis-owned disposable internal state.

Recommended categories are:

```text
.planaxis/
├── cache/
└── temp/
```

Possible contents include:

- thumbnails;
- transcoded textures;
- optimized derived meshes;
- generated previews;
- temporary AI workflow files;
- other reconstructible caches.

PlanAxis MAY create, replace, or delete contents under `.planaxis/` as needed.

No authoritative or otherwise irreplaceable project information may exist only under
`.planaxis/`.

No durable project descriptor may require `.planaxis/` contents for correct interpretation.

Deleting the complete `.planaxis/` directory MUST NOT destroy project information.

# 11. Write ownership

Project Format 1.0 establishes the following write expectations.

## 11.1. Manifest and architecture

PlanAxis MUST NOT silently rewrite `planaxis.project.json` or files under `architecture/`
merely because a project was opened or viewed.

Changes to the manifest or architecture require an explicit operation whose purpose includes
modifying that durable data.

## 11.2. Assets and references

PlanAxis MUST NOT silently modify user-provided durable asset or reference content merely
because it was read.

Creation, import, normalization, replacement, or deletion of durable assets and references
requires an explicit operation.

## 11.3. Designs

When design editing is introduced, PlanAxis MAY persist ordinary explicit design-editing
operations under `designs/`.

## 11.4. Outputs

PlanAxis MAY create generated artifacts under `outputs/` as part of an explicitly initiated
rendering or generation operation.

## 11.5. Internal state

PlanAxis owns `.planaxis/` completely and MAY modify it without separate user confirmation
during normal project operation.

## 11.6. Durable descriptor writes

When PlanAxis writes durable JSON descriptors, implementations SHOULD use an atomic
replacement strategy where the host filesystem permits it, so interruption does not leave a
partially written authoritative file.

---

# 12. Portability

A conforming PlanAxis project is intended to be portable as a directory tree.

Copying the complete durable project directory to another supported system MUST NOT require
repair of persistent absolute filesystem references.

Project authors SHOULD avoid filesystem constructs that reduce cross-platform portability,
including filenames that differ only by case or names prohibited by common supported
filesystems.

The project folder MAY be:

- copied to another machine;
- archived;
- backed up;
- stored on a NAS;
- synchronized by external file-sync software;
- placed under version control.

None of these storage mechanisms change PlanAxis Project Format semantics.

---

# 13. Versioning and compatibility

## 13.1. Independent versioning

The PlanAxis Project Format is versioned independently from:

- the PlanAxis application;
- Apartment SVG;
- future material-descriptor formats;
- future model-asset formats;
- future design-scenario formats.

For example, a future project may contain:

```text
PlanAxis Project Format 1.x
Apartment SVG 2.2
PlanAxis Material 1.x
PlanAxis Design 1.x
```

without requiring those formats to share a version number.

## 13.2. Unsupported versions

An implementation that does not support the manifest's project-format schema MUST reject
project-format interpretation with a clear error.

It MUST NOT guess the meaning of an unsupported project-format version.

## 13.3. Migration

A future PlanAxis version MAY provide an explicit project migration from an older supported
format to a newer format.

A migration that modifies durable project data MUST be deliberate and SHOULD use
failure-safe writes.

Merely opening a project SHOULD NOT silently change its project-format version.

---

# 14. Future subordinate formats

Project Format 1.0 intentionally reserves locations for later formats without specifying
them.

Possible future independently versioned schema identifiers include:

```text
planaxis-material/1.0
planaxis-model-asset/1.0
planaxis-design/1.0
```

These names are illustrative until their own specifications are accepted.

Future subordinate formats MUST preserve the Project Format path and filesystem-boundary
rules when they reference project resources.

# 15. Minimal conforming example

Directory:

```text
my-apartment/
├── planaxis.project.json
└── architecture/
    └── existing.svg
```

Manifest:

```json
{
  "schema": "planaxis-project/1.0",
  "name": "My apartment renovation",
  "architecture": {
    "active": "architecture/existing.svg"
  }
}
```

The project is Project Format conformant if the directory and manifest satisfy this
specification and the referenced regular file is accessible under the project root without
symbolic-link traversal.

The referenced `existing.svg` may still fail Apartment SVG validation. Such failure does not
by itself make the project container invalid.

# 16. Non-conforming examples

## 16.1. Absolute active-architecture path

```json
{
  "schema": "planaxis-project/1.0",
  "name": "My apartment renovation",
  "architecture": {
    "active": "/home/user/apartment.svg"
  }
}
```

Invalid because persistent project references must be project-relative.

## 16.2. Parent traversal

```json
{
  "schema": "planaxis-project/1.0",
  "name": "My apartment renovation",
  "architecture": {
    "active": "architecture/../outside.svg"
  }
}
```

Invalid because `..` segments are prohibited.

## 16.3. Active file outside `architecture/`

```json
{
  "schema": "planaxis-project/1.0",
  "name": "My apartment renovation",
  "architecture": {
    "active": "references/old-plan.svg"
  }
}
```

Invalid because the active architecture must be located under `architecture/`.

## 16.4. Unknown manifest property

```json
{
  "schema": "planaxis-project/1.0",
  "name": "My apartment renovation",
  "description": "Renovation project",
  "architecture": {
    "active": "architecture/existing.svg"
  }
}
```

Invalid in Project Format 1.0 because the manifest schema is closed and `description` is not
defined.

---

# 17. Conformance summary

A PlanAxis Project Format 1.0 implementation MUST at minimum enforce:

1. the required `planaxis.project.json` manifest and supported schema identifier;
2. the closed manifest structure and required values;
3. the required `architecture/` directory and accessible active `.svg` regular file;
4. canonical project-relative path syntax;
5. project-root containment for project resource access;
6. prohibition of symbolic-link traversal below the canonical project root;
7. separation between project-format conformance and Apartment SVG conformance;
8. the disposable nature of `.planaxis/`;
9. the portability rule prohibiting persistent dependence on absolute external paths.

The format intentionally leaves future asset and design descriptor semantics to separate
specifications.

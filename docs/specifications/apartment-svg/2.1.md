# Apartment Interior Design SVG Specification

**Version:** 2.1  
**Status:** Normative specification  
**Language:** English  
**Schema identifier:** `apartment-svg/2.1`

---

# 1. Purpose and scope

This document is the **normative specification** of an accurate, machine-readable, manually editable SVG-based geometric and semantic model of an apartment.

The purpose of the specification is to ensure that when interpreting a valid SVG document:

- no visual guessing is required;
- no natural-language inference is required;
- two independent implementations interpret the same SVG in the same way;
- the attribute set, data type, and meaning of every structural element are unambiguous;
- geometric and referential errors can be validated automatically;
- presentation (`style`, CSS, colors, strokes) does not influence geometric or semantic interpretation in any way.

The current version of the format handles a single apartment level.

---

# 2. Normative keywords

The following expressions have normative meaning in this document:

- **REQUIRED / MUST** – violating the rule results in an invalid document.
- **PROHIBITED / MUST NOT** – the given construct may not be used.
- **RECOMMENDED / SHOULD** – strongly recommended, but deviation is permitted when justified.
- **NOT RECOMMENDED / SHOULD NOT** – should be avoided, but is permitted when justified.
- **OPTIONAL / MAY** – may be used freely.

If an example and a normative rule contradict each other, the normative rule takes precedence.

---

# 3. Conformance levels

A document can be examined at three separate levels.

## 3.1. XML-conformant

The SVG is syntactically valid XML.

## 3.2. Schema-conformant

The document:

- uses only permitted structural elements;
- contains every required attribute;
- contains no prohibited attribute;
- has attribute values that conform to the specified data types and enums.

## 3.3. Geometrically conformant

In addition, the schema-conformant document also satisfies the geometric, topological, and referential invariants.

Hereinafter, the expression **valid apartment SVG** means a geometrically conformant document.

---

# 4. Fundamental modeling principles

## 4.1. Single source of geometric truth

The exact 2D geometry is derived exclusively from the SVG geometric attributes.

For example:

```xml
<rect x="100" y="200" width="12" height="412" />
```

The element above represents a 12 × 412 cm rectangle.

Storing the same dimension separately in `data-width`, `data-length`, `data-depth`, or a similar attribute is PROHIBITED.

## 4.2. 1 SVG unit = 1 cm

Every numeric SVG coordinate and geometric dimension is interpreted in centimeters.

## 4.3. Coordinate system

The 2D system:

- `+X` = right;
- `+Y` = down.

The 3D system:

- `+X` = right;
- `+Y` = down;
- `+Z` = up.

## 4.4. Prohibition of transformations

The `transform` attribute is PROHIBITED on elements that are part of the semantic model and on their parent groups.

`transform` may be used exclusively within the `annotations` group.

## 4.5. CSS and presentation

The following are permitted:

- internal `<style>`;
- external CSS via an `<?xml-stylesheet ...?>` processing instruction;
- `class`;
- `style`;
- `fill`;
- `stroke`;
- other exclusively visual SVG/CSS properties.

These are **not part of the semantic model**, therefore a parser or validator may not use them for geometric or functional inference.

# 5. Lexical data types

The following type names are normative abbreviations in the remainder of the specification.

## 5.1. `Id`

Format:

```text
[A-Za-z][A-Za-z0-9._-]*
```

Examples:

```text
wall-living-left
window-01
camera.main
```

The `id` MUST be unique at document level.

## 5.2. `Ref`

A string pointing to the `id` value of another element.

The referenced element must exist and must have the appropriate `data-kind` type.

## 5.3. `Number`

A finite decimal number:

```text
-?[0-9]+(\.[0-9]+)?
```

PROHIBITED:

- exponential notation (`1e3`);
- `NaN`;
- `Infinity`;
- a unit in the value (`12cm`).

## 5.4. `PositiveNumber`

A `Number` for which:

```text
value > 0
```

## 5.5. `NonNegativeNumber`

A `Number` for which:

```text
value >= 0
```

## 5.6. `Boolean`

Exactly one of the following two values:

```text
true
false
```

## 5.7. `Angle360`

A `Number` for which:

```text
0 <= value < 360
```

## 5.8. `PitchAngle`

A `Number` for which:

```text
-90 < value < 90
```

## 5.9. Geometric tolerance

The normative tolerance for geometric comparison is:

```text
EPSILON = 0.01 cm
```

Two coordinates are geometrically equal if:

```text
abs(a - b) <= EPSILON
```

It is RECOMMENDED that the parser handle input decimal values using exact decimal arithmetic.

## 5.10. `Latitude`

WGS84 geographic latitude in decimal degrees.

Its type is `Number`, and:

```text
-90 <= value <= 90
```

Sign convention:

```text
value > 0  -> northern latitude
value < 0  -> southern latitude
value = 0  -> Equator
```

A degree symbol or cardinal-direction letter (`N`, `S`) in the value is PROHIBITED.

## 5.11. `Longitude`

WGS84 geographic longitude in decimal degrees.

Its type is `Number`, and:

```text
-180 <= value <= 180
```

Sign convention:

```text
value > 0  -> eastern longitude
value < 0  -> western longitude
value = 0  -> Greenwich prime meridian
```

A degree symbol or cardinal-direction letter (`E`, `W`) in the value is PROHIBITED.

`-180` and `180` represent the same meridian; in a new document, `180` is the RECOMMENDED canonical form.

## 5.12. `ElevationMeters`

The elevation of the location **in meters above mean sea level (MSL)**.

Its type is `Number`.

A negative value is permitted for a location below sea level.

The value is not WGS84 ellipsoidal height. If the source provides only ellipsoidal height, it must be converted to MSL elevation before being written to the document.

## 5.13. `TimeZoneId`

A non-empty string that is a zone identifier defined by the IANA Time Zone Database.

Example:

```text
Europe/Budapest
America/New_York
Asia/Tokyo
```

A fixed UTC offset (`+02:00`, `UTC+2`) is PROHIBITED instead of a time zone identifier.

The `TimeZoneId` represents civil timekeeping rules, therefore historical and future UTC offsets may depend on the date.

# 6. Document structure

The minimum structure of a conformant document is:

```xml
<?xml version="1.0" encoding="UTF-8"?>

<svg
    xmlns="http://www.w3.org/2000/svg"
    viewBox="..."
    data-schema="apartment-svg"
    data-schema-version="2.1"
    data-unit="cm">

    <metadata>...</metadata>

    <g id="spaces">...</g>
    <g id="walls">...</g>
    <g id="windows">...</g>
    <g id="doors">...</g>
    <g id="fixed-elements">...</g>
    <g id="utilities">...</g>
    <g id="cameras">...</g>
    <g id="annotations">...</g>

</svg>
```

## 6.1. Required top-level groups

Each of the following eight groups must appear exactly once:

| `id` | Function |
|---|---|
| `spaces` | functional zones |
| `walls` | walls |
| `windows` | windows |
| `doors` | door openings |
| `fixed-elements` | fixed architectural and mechanical elements |
| `utilities` | electrical and IT points |
| `cameras` | defined cameras |
| `annotations` | graphics exclusively assisting human reading |

An empty group is permitted.

The order of the groups is not semantic, but the order above is RECOMMENDED.

## 6.2. Other permitted root-level SVG elements

The following non-semantic elements may optionally appear directly under `<svg>`:

```text
style
defs
title
desc
```

Their content is to be ignored from the perspective of the core geometric model.

External CSS may also be referenced with an `xml-stylesheet` processing instruction placed at the beginning of the XML document.

## 6.3. Unknown top-level group

An unknown direct `<g>` child is a schema error.

An experimental extension may be used exclusively with an identifier of this form:

```text
x-*
```

For example:

```xml
<g id="x-furniture-prototype">...</g>
```

A 2.1 parser may ignore the contents of such a group.

# 7. Root `<svg>` element

## 7.1. Required attributes

| Attribute | Type | Required | Value / meaning |
|---|---|---:|---|
| `xmlns` | string | yes | exactly `http://www.w3.org/2000/svg` |
| `viewBox` | 4 × `Number` | yes | `minX minY width height` |
| `data-schema` | enum | yes | exactly `apartment-svg` |
| `data-schema-version` | enum | yes | exactly `2.1` |
| `data-unit` | enum | yes | exactly `cm` |

`viewBox.width > 0` and `viewBox.height > 0`.

Every point of semantic geometry must be within the area of the `viewBox`. Elements in `annotations` may extend beyond it.

```json
    "z": "up",

      "90": "+y",

  "level": {
    "id": "level-0",
    "baseZ": 0,
    "defaultCeilingHeight": 242
  }
}
```

The same with optional geographic location data:

```json
{
  "schema": "apartment-svg/2.1",
  "project": {
    "name": "Apartment renovation",
    "units": "cm"
  },
  "coordinateSystem": {
    "x": "right",
    "y": "down",
    "z": "up",
    "headingDegrees": {
      "0": "+x",
      "90": "+y",

    "id": "level-0",

    "latitude": 47.4979,
    "longitude": 19.0402,
    "elevationMeters": 105,
    "timeZone": "Europe/Budapest",
    "northHeading": 270
  }
}
```

## 8.1. Required fields

| JSON path | Type | Required | Constraint |
|---|---|---:|---|
| `schema` | string | yes | `apartment-svg/2.1` |
| `project.name` | non-empty string | yes | project name |
| `project.units` | enum | yes | `cm` |
| `coordinateSystem.x` | enum | yes | `right` |
| `coordinateSystem.y` | enum | yes | `down` |
| `coordinateSystem.z` | enum | yes | `up` |
| `coordinateSystem.headingDegrees.0` | enum | yes | `+x` |
| `coordinateSystem.headingDegrees.90` | enum | yes | `+y` |
| `coordinateSystem.headingDegrees.180` | enum | yes | `-x` |
| `coordinateSystem.headingDegrees.270` | enum | yes | `-y` |
| `level.id` | `Id` | yes | one level in the current version |
| `level.baseZ` | `Number` | yes | typically `0` |
| `level.defaultCeilingHeight` | `PositiveNumber` | yes | cm |

The values of `project.units` and the root `data-unit` must match.

## 8.2. Optional geographic location and orientation

The document may optionally contain a `location` object.

Example:

```json
"location": {
  "latitude": 47.4979,
  "longitude": 19.0402,
  "elevationMeters": 105,
  "timeZone": "Europe/Budapest",
  "northHeading": 270
}
```

The `location` object describes the **permanent geographic and orientation data** of the apartment. It is not rendering state.

### 8.2.1. Attribute schema

| JSON path | Type | Required | Meaning / constraint |
|---|---|---:|---|
| `location.latitude` | `Latitude` | conditional | required when `location` is present; WGS84 latitude |
| `location.longitude` | `Longitude` | conditional | required when `location` is present; WGS84 longitude |
| `location.northHeading` | `Angle360` | conditional | required when `location` is present; direction of true north in the SVG coordinate system |
| `location.elevationMeters` | `ElevationMeters` | no | elevation above MSL in meters |
| `location.timeZone` | `TimeZoneId` | no | civil time zone of the location |

The entire `location` object is OPTIONAL.

If the `location` object is present, the following three fields are jointly REQUIRED:

```text
latitude
longitude
northHeading
```

`elevationMeters` and `timeZone` are optional.

The parser MUST NOT automatically infer missing `elevationMeters` or `timeZone` values from the coordinates and treat them as part of the canonical model.

### 8.2.2. Exact meaning of `northHeading`

`northHeading` specifies the direction of **geographic true north** in the top-view coordinate system of the apartment SVG.

It does not represent magnetic north.

It uses the same heading convention as the cameras:

```text
0°   = +X = right
90°  = +Y = down
180° = -X = left
270° = -Y = up
```

For example:

```json
"northHeading": 270
```

means: true north is upward in the SVG, that is, in the `-Y` direction.

`northHeading` applies globally to the entire SVG coordinate system.

### 8.2.3. Converting geographic azimuth to SVG heading

The geographic azimuth convention in the specification is:

```text
0°   = true north
90°  = east
180° = south
270° = west
```

The azimuth increases clockwise.

If:

```text
N = location.northHeading
A = geographicAzimuth
```

then the SVG heading of the given geographic direction is:

```text
svgHeading = normalize360(N + A)
```

where:

```text
normalize360(x) = ((x % 360) + 360) % 360
```

Example:

```text
northHeading = 270°
solarAzimuth = 90°   (east)

svgHeading = normalize360(270 + 90)
           = 0°
           = +X
```

### 8.2.4. Deriving sun direction in 3D coordinates

If an external astronomical algorithm determines for the rendered instant:

```text
A = solar azimuth
E = solar elevation angle
```

then first:

```text
H = normalize360(location.northHeading + A)
```

In the SVG/3D coordinate system, the unit vector pointing from the observer toward the Sun is:

```text
sunVector.x = cos(E) * cos(H)
sunVector.y = cos(E) * sin(H)
sunVector.z = sin(E)
```

where the arguments of the trigonometric functions must be evaluated in radians.

The `sunVector` above points **from the scene toward the Sun**.

The direction of the light ray arriving from the Sun toward the scene is its opposite:

```text
incomingLightDirection = -sunVector
```

This definition is renderer-independent; a Three.js or other rendering engine must map this semantics appropriately to its own light object.

### 8.2.5. Date and time are not part of the SVG

Date and time are **not permanent properties of the apartment**, therefore they are not to be stored in the metadata section of the canonical apartment SVG.

The rendering / simulation request specifies the examined instant as a separate runtime parameter.

The RECOMMENDED format is an ISO 8601 timestamp that also contains an offset, for example:

```text
2026-10-18T17:42:00+02:00
```

If the runtime request provides only a local civil date and time without a UTC offset, then `location.timeZone` is required to convert it to an unambiguous UTC instant.

If `location.timeZone` is missing, the renderer MUST NOT guess how to convert a local time without an offset into a UTC instant.

### 8.2.6. Solar-aware capability

At least the following data are required for geometric solar-position calculation:

```text
location.latitude
location.longitude
location.northHeading
render-time date/time as an unambiguous instant
```

`elevationMeters` may be used for a higher-accuracy solar-position, refraction, or atmospheric model.

`timeZone` is not required if the rendering time already contains an unambiguous UTC instant or explicit UTC offset; however, it is required when local civil time is provided as input.

The **geometric position** of the Sun (azimuth and elevation angle) can be derived deterministically using the appropriate astronomical model.

The **actual color and intensity** of direct sunlight cannot be derived solely from the apartment SVG, because they are also influenced, among other things, by atmospheric and weather conditions.

A renderer may use an explicit clear-sky or other atmospheric model, but:

- the model used is configuration of the rendering system, not geometry of the apartment SVG;
- in the absence of actual weather data, the renderer may not claim that it reproduces real meteorological conditions;
- the color and intensity of the light must not be written back into the SVG as canonical geometric facts.

### 8.2.7. Missing `location`

If `location` is not specified:

- the document may still be fully schema-conformant;
- the parser may not assume a default geographic location;
- the parser may not assume a default north direction;
- rendering based on geographically accurate solar position may only be performed with location data supplied separately at runtime.

## 8.3. Metadata extensions

Unknown keys in the objects above are PROHIBITED unless the key name begins with the `x-` prefix. An `x-*` metadata key must not modify core semantics.

# 9. Common rules for semantic elements

Every semantic element:

1. has a unique `id` attribute;
2. has a `data-kind` attribute;
3. is a direct child of its corresponding top-level group;
4. does not have a `transform` attribute.

Nesting semantic elements inside one another is PROHIBITED.

For example, an additional `<rect>` may not appear inside a wall.

## 9.1. Presentation attributes

Standard SVG presentation attributes not listed in the normative tables — for example `class`, `style`, `fill`, `stroke`, `opacity` — are permitted, but the core parser must ignore them.

An SVG attribute or construct that modifies geometry but is not permitted by this specification may not be used for semantic inference.

## 9.2. Extension attributes

An unknown `data-*` attribute is PROHIBITED unless its name is:

```text
data-x-*
```

For example:

```xml
data-x-source="survey-2026"
```

The core parser ignores the `data-x-*` attribute.

# 10. Status type

Where the specification permits a `data-status` attribute, its type is:

```text
fixed | modifiable | proposal
```

Meaning:

| Value | Meaning |
|---|---|
| `fixed` | cannot be changed in the current model |
| `modifiable` | existing, but may be modified / demolished / relocated during design |
| `proposal` | not existing, but a planned new element |

The `status` is a **design status**, not a geometric type.

# 11. `spaces` – functional zones

## 11.1. Permitted element

Exclusively:

```xml
<polygon>
```

## 11.2. Attribute schema

| Attribute | Type | Required | Meaning |
|---|---|---:|---|
| `id` | `Id` | yes | unique identifier |
| `points` | coordinate list | yes | polygon of the zone |
| `data-kind` | enum | yes | `zone` |
| `data-name` | non-empty string | yes | human-readable name |
| `data-function` | enum | yes | see 11.3 |
| `data-function-description` | non-empty string | conditional | required when `data-function="other"` |
| `data-enclosure` | enum | yes | `closed`, `partial`, `open` |

## 11.3. `data-function`

Permitted values:

```text
living-room
dining
kitchen
bedroom
bathroom
toilet
hall
corridor
entrance
home-office
storage
utility
balcony
other
```

If:

```text
data-function="other"
```

then `data-function-description` is REQUIRED.

If `data-function!="other"`, then `data-function-description` is PROHIBITED.

## 11.4. `data-enclosure`

| Value | Meaning |
|---|---|
| `closed` | physically enclosed room |
| `partial` | partially bounded functional zone |
| `open` | physically open functional zone |

`data-enclosure` does not create a wall.

## 11.5. Polygon rules

The polygon must:

- have at least 3 distinct vertices;
- have positive area;
- not self-intersect;
- not be required to repeat its last point;
- not extend into the interior of a wall.

The interior areas of two zones may not overlap in version 2.1. Their boundaries may be shared.

# 12. `walls` – walls

## 12.1. Permitted element

Exclusively:

```xml
<rect>
```

## 12.2. Attribute schema

| Attribute | Type | Required | Meaning |
|---|---|---:|---|
| `id` | `Id` | yes | wall identifier |
| `x` | `Number` | yes | left X |
| `y` | `Number` | yes | top Y |
| `width` | `PositiveNumber` | yes | geometric width |
| `height` | `PositiveNumber` | yes | geometric height in the plane |
| `data-kind` | enum | yes | `wall` |
| `data-axis` | enum | yes | `x` or `y` |
| `data-height` | `PositiveNumber` | no | 3D wall height |
| `data-class` | enum | yes | `interior` or `exterior` |
| `data-status` | `Status` | yes | status |

## 12.3. `data-axis`

`data-axis` denotes the longitudinal axis of the wall.

```text
x = horizontal wall, the wall length is along X
y = vertical wall, the wall length is along Y
```

### Required consistency

If:

```text
data-axis="x"
```

then:

```text
width > height
```

If:

```text
data-axis="y"
```

then:

```text
height > width
```

A square wall (`width == height`) is not permitted. Such a structural element should be a `column` or another fixed-element.

## 12.4. Wall thickness and wall length

If `data-axis="x"`:

```text
length    = width
thickness = height
centerlineY = y + height / 2
```

If `data-axis="y"`:

```text
length    = height
thickness = width
centerlineX = x + width / 2
```

## 12.5. 3D wall height

If `data-height` is present, it must be used.

If it is not present:

```text
effectiveWallHeight = metadata.level.defaultCeilingHeight
```

## 12.6. Wall overlaps

The rectangles of two walls may intersect or overlap for corner and junction formation.

Such an overlap is to be interpreted as a geometric union.

## 13.1. Permitted element

Exclusively:

```xml
<rect>
```

## 13.2. Attribute schema

| Attribute | Type | Required | Meaning |
|---|---|---:|---|
| `id` | `Id` | yes | window identifier |
| `x` | `Number` | yes | opening footprint |
| `y` | `Number` | yes | opening footprint |
| `width` | `PositiveNumber` | yes | opening footprint |
| `height` | `PositiveNumber` | yes | opening footprint |
| `data-kind` | enum | yes | `window` |
| `data-wall` | `Ref<wall>` | yes | supporting wall |
| `data-sill-height` | `NonNegativeNumber` | yes | sill / lower edge Z |
| `data-opening-height` | `PositiveNumber` | yes | vertical height of the opening |
| `data-opening-type` | enum | no | see below |
| `data-frame-material` | enum | no | see below |
| `data-frame-material-description` | non-empty string | conditional | required when `data-frame-material="other"` |
| `data-frame-color` | string | no | presentation / design metadata |
| `data-glass-type` | enum | no | see below |
| `data-glass-type-description` | non-empty string | conditional | required when `data-glass-type="other"` |
| `data-radiator-below` | `Ref<radiator>` | no | associated radiator |
| `data-status` | `Status` | yes | status |

## 13.3. `data-opening-type`

Permitted values:

```text
fixed
casement
tilt
tilt-turn
sliding
```

| Value | Meaning |
|---|---|
| `fixed` | not openable |
| `casement` | side-hinged opening sash |
| `tilt` | tilt |
| `tilt-turn` | tilt-and-turn |
| `sliding` | sliding |

The enum describes the operating type of the window, **not** the exact sash geometry.

## 13.4. `data-frame-material`

```text
wood
plastic
aluminium
steel
other
```

If its value is `other`, then `data-frame-material-description` is REQUIRED.
For any other value, `data-frame-material-description` is PROHIBITED.

## 13.5. `data-glass-type`

```text
clear
frosted
tinted
other
```

If its value is `other`, then `data-glass-type-description` is REQUIRED.
For any other value, `data-glass-type-description` is PROHIBITED.

## 13.6. Geometric relationship to the wall

The `data-axis` value of the wall referenced by `data-wall` determines the required geometry.

### If the wall has `data-axis="x"`

The window:

```text
window.y      == wall.y
window.height == wall.height
window.x      >= wall.x
window.x + window.width <= wall.x + wall.width
```

### If the wall has `data-axis="y"`

The window:

```text
window.x     == wall.x
window.width == wall.width
window.y     >= wall.y
window.y + window.height <= wall.y + wall.height
```

Equalities must be checked with `EPSILON` tolerance.

## 13.7. Window width

If the wall axis is `x`:

```text
openingWidth = window.width
```

If the wall axis is `y`:

```text
openingWidth = window.height
```

A separate `data-opening-width` attribute is PROHIBITED.

## 13.8. Vertical geometry

Let:

```text
wallHeight = effective wall height
```

Required:

```text
data-sill-height + data-opening-height <= wallHeight
```

The 3D opening of the window is:

```text
Zmin = data-sill-height
Zmax = data-sill-height + data-opening-height
```

# 14. `doors` – doors

## 14.1. Model

A `door` element defines the following:

1. the exact 2D footprint of the door opening in the wall;
2. the 3D height of the opening;
3. for a normal hinged door, the plan-view point of the hinge axis;
4. the free endpoint of the door leaf when fully open to 90°.

The model **does not** use viewpoint-dependent semantic attributes such as `left`, `right`, `inward`, or `outward`.

## 14.2. Permitted element

Exclusively:

```xml
<rect>
```

## 14.3. Attribute schema

| Attribute | Type | Required | Condition / meaning |
|---|---|---:|---|
| `id` | `Id` | yes | door identifier |
| `x` | `Number` | yes | opening footprint |
| `y` | `Number` | yes | opening footprint |
| `width` | `PositiveNumber` | yes | opening footprint |
| `height` | `PositiveNumber` | yes | opening footprint |
| `data-kind` | enum | yes | `door` |
| `data-wall` | `Ref<wall>` | yes | supporting wall |
| `data-door-type` | enum | yes | door type |
| `data-opening-height` | `PositiveNumber` | yes | vertical opening height |
| `data-hinge-x` | `Number` | conditional | required for `hinged` |
| `data-hinge-y` | `Number` | conditional | required for `hinged` |
| `data-open-leaf-x` | `Number` | conditional | required for `hinged` |
| `data-open-leaf-y` | `Number` | conditional | required for `hinged` |
| `data-status` | `Status` | yes | status |

## 14.4. `data-door-type`

Permitted values:

```text
hinged
sliding
opening-only
```

| Value | Meaning |
|---|---|
| `hinged` | a single hinged door leaf modeled with a 90° reference state |
| `sliding` | sliding door; the 2.1 core schema records only the opening |
| `opening-only` | wall opening without a door leaf |

### Conditional attribute rules

If:

```text
data-door-type="hinged"
```

then all four of the following attributes are REQUIRED:

```text
data-hinge-x
data-hinge-y
data-open-leaf-x
data-open-leaf-y
```

If:

```text
data-door-type="sliding"
```

or:

```text
data-door-type="opening-only"
```

then the four hinge/open-leaf attributes are PROHIBITED.

## 14.5. Geometric relationship to the wall

The opening rectangle must exactly cover the full thickness of the wall.

### If the wall has `data-axis="x"`

```text
door.y      == wall.y
door.height == wall.height
door.x      >= wall.x
door.x + door.width <= wall.x + wall.width
```

The opening width is:

```text
openingWidth = door.width
```

### If the wall has `data-axis="y"`

```text
door.x     == wall.x
door.width == wall.width
door.y     >= wall.y
door.y + door.height <= wall.y + wall.height
```

The opening width is:

```text
openingWidth = door.height
```

## 14.6. Door height

Required:

```text
data-opening-height <= effectiveWallHeight
```

The vertical range of the opening is:

```text
Zmin = 0
Zmax = data-opening-height
```

The 2.1 core schema assumes a door without a threshold.

## 14.7. Exact definition of the `hinge` point

The `hinge` point is the plan-view projection of the rotation axis of the hinged door.

The point:

- is on the centerline of the supporting wall;
- coincides with one of the two longitudinal endpoints of the door opening.

### Horizontal wall (`data-axis="x"`)

```text
centerY = wall.y + wall.height / 2
```

The hinge is exactly one of the following two:

```text
(door.x,              centerY)
(door.x + door.width, centerY)
```

### Vertical wall (`data-axis="y"`)

```text
centerX = wall.x + wall.width / 2
```

The hinge is exactly one of the following two:

```text
(centerX, door.y)
(centerX, door.y + door.height)
```

Any other hinge position is a schema-geometric error.

## 14.8. Implicit geometry of the closed door leaf

The closed door leaf is not stored with separate attributes.

Its free endpoint in the closed state can be determined unambiguously from the hinge.

### Horizontal wall

If:

```text
hinge = (door.x, centerY)
```

then:

```text
closedFreeEnd = (door.x + door.width, centerY)
```

If:

```text
hinge = (door.x + door.width, centerY)
```

then:

```text
closedFreeEnd = (door.x, centerY)
```

### Vertical wall

If:

```text
hinge = (centerX, door.y)
```

then:

```text
closedFreeEnd = (centerX, door.y + door.height)
```

If:

```text
hinge = (centerX, door.y + door.height)
```

then:

```text
closedFreeEnd = (centerX, door.y)
```

## 14.9. Exact definition of the `open-leaf` point

The `open-leaf` point is the **free endpoint of the door leaf when fully open to 90°**.

The hinge point does not move.

The length of the door leaf is:

```text
leafLength = openingWidth
```

Required:

```text
distance(hinge, openLeaf) == leafLength
```

and the open door leaf is perpendicular to the longitudinal axis of the supporting wall.

### Horizontal wall

Required:

```text
openLeaf.x == hinge.x
abs(openLeaf.y - hinge.y) == leafLength
```

Therefore exactly two geometrically possible 90° states exist:

```text
(hinge.x, hinge.y - leafLength)
(hinge.x, hinge.y + leafLength)
```

### Vertical wall

Required:

```text
openLeaf.y == hinge.y
abs(openLeaf.x - hinge.x) == leafLength
```

Therefore exactly two geometrically possible 90° states exist:

```text
(hinge.x - leafLength, hinge.y)
(hinge.x + leafLength, hinge.y)
```

## 14.10. Opening direction

The opening direction follows exclusively from the geometric data of `hinge` and `open-leaf`.

For example, for a horizontal wall:

```text
openLeaf.y < hinge.y  -> the door opens toward the -Y side
openLeaf.y > hinge.y  -> the door opens toward the +Y side
```

For a vertical wall:

```text
openLeaf.x < hinge.x  -> the door opens toward the -X side
openLeaf.x > hinge.x  -> the door opens toward the +X side
```

Storing a viewpoint-dependent `left/right/inward/outward` attribute in the specification is PROHIBITED.

## 14.11. Door opening arc

The door opening arc is:

- derived, presentation geometry;
- not part of the source of truth;
- may be stored exclusively in the `annotations` group or generated during rendering.

The center of the arc is the hinge, its radius is `leafLength`, and its start and end directions are the directions of the closed and open door leaf.

### `fixed-object`


# 17. `cameras` – cameras

## 17.1. Permitted element

Exclusively:

```xml
<circle>
```

## 17.2. Attribute schema

| Attribute | Type | Required | Constraint |
|---|---|---:|---|
| `id` | `Id` | yes | camera identifier |
| `cx` | `Number` | yes | X |
| `cy` | `Number` | yes | Y |
| `r` | `PositiveNumber` | yes | marker only |
| `data-kind` | enum | yes | `camera` |
| `data-z` | `NonNegativeNumber` | yes | camera height |
| `data-heading` | `Angle360` | yes | horizontal direction |
| `data-pitch` | `PitchAngle` | yes | vertical direction |
| `data-horizontal-fov` | `Number` | yes | `0 < FOV < 180` |

## 17.3. Heading

```text
0°   = +X
90°  = +Y
180° = -X
270° = -Y
```

The angle increases clockwise in the top-view XY plane.

## 17.4. Pitch

```text
0°  = horizontal
>0° = looks downward
<0° = looks upward
```

This convention is mandatory.

## 17.5. Camera position

The 3D point of the camera may not be inside the physical volume of a wall or fixed-element.

For a wall, the volume is:

```text
XY = wall footprint
Z  = [level.baseZ, level.baseZ + effectiveWallHeight]
```

For a fixed-element:

```text
XY = element footprint
Z  = [data-base-z, data-base-z + data-height]
```

An element collides with the camera only if the camera XY point is inside the footprint **and** the camera `data-z` value falls within the element's Z range.

The marker `r` does not participate in collision detection.

## 19.2. `data-radiator-below`

# 20. Collisions and overlaps

## 20.1. Wall–wall

Permitted.

## 20.2. Window–wall

Required, but exclusively with the footprint of its own wall referenced by `data-wall`, according to rule 13.6.

## 20.3. Door–wall

Required, but exclusively with the footprint of its own wall referenced by `data-wall`, according to rule 14.5.

## 20.4. Window–window

Positive-area overlap between two windows is PROHIBITED.

## 20.5. Door–door

Positive-area overlap between two door openings is PROHIBITED.

## 20.6. Door–window

Positive-area overlap is PROHIBITED.

## 20.7. Zone–wall

The interior of a zone may not overlap the interior of a wall footprint.

Boundary contact is permitted.

# 22. Canonical interpretation order

A parser should process the document in the following logical order:

1. XML parse.
2. Validate root attributes.
3. Parse and validate metadata.
4. Check required top-level groups.
5. Build unique `id` index.
6. Schema-validate element types.
7. Resolve references.
8. Validate wall geometry and wall axis.
9. Validate opening–wall relationships.
10. Validate door hinge/open-leaf invariants.
11. Validate zone topology.
12. Validate fixed-elements.
13. Validate utilities.
14. Validate cameras.
15. Check overlap rules.
16. Only then may the 3D model be built.

```text
wall centerX = 420 + 12 / 2 = 426

             = (336, 300)
```

Valid.

## 24.2. Vertical wall, hinge at bottom, opening to the right

```xml
data-hinge-x="426"
data-hinge-y="390"

data-open-leaf-y="390"
```

Derivation:

```text
leafLength = 90
516 = 426 + 90
```

Valid.

## 24.3. Horizontal wall, hinge on the left, opening upward

Assume:

```text
door = x:200, y:100, width:90, height:12
wall axis = x
wall centerY = 106
```

The correct data are:

```xml
data-hinge-x="200"
data-hinge-y="106"

data-open-leaf-x="200"
```

because:

```text
16 = 106 - 90
```

## 24.4. Invalid hinge

```xml
data-hinge-x="426"
data-hinge-y="320"
```

is invalid for a vertical wall, because the hinge is not located at the upper or lower longitudinal end of the door opening.

## 24.5. Invalid open-leaf

```xml
data-hinge-x="426"
data-hinge-y="300"

data-open-leaf-x="350"
data-open-leaf-y="320"
```

is invalid because:

- the door leaf is not perpendicular to the wall;
- the distance is not exactly the opening width;
- the state is not a 90° reference state.

# 27. Version changes

## 27.1. Changes compared to version 2.0

Version 2.1 extends the 2.0 specification exclusively with formal support for optional geographic location and orientation metadata.

New features:

1. `Latitude`, `Longitude`, `ElevationMeters`, and `TimeZoneId` lexical types;
2. optional `metadata.location` object;
3. required `latitude`, `longitude`, and `northHeading` when the `location` object is present;
4. optional `elevationMeters` and `timeZone`;
5. explicit true-north semantics of `northHeading`;
6. normative geographic azimuth → SVG heading transformation;
7. normative sun direction → 3D unit-vector transformation;
8. explicit separation of render-time date/time and permanent apartment metadata;
9. rule for the relationship between local time without an offset and `timeZone`;
10. explicit boundary between deterministic solar geometry and the modeling of atmospheric light intensity/color.

All other rules of 2.0 that are independent of the extension above remain unchanged.

## 27.2. Changes compared to version 1.0

The most important stricter rules introduced in version 2.0:

1. normative `MUST / MUST NOT / SHOULD / MAY` semantics;
2. explicit lexical data types;
3. explicit `EPSILON`;
4. required top-level group schema;
5. required and conditional attribute tables;
6. explicit `data-axis` on walls;
7. exact window–wall geometric invariants;
8. introduction of `data-door-type`;
9. mathematically exact hinge and open-leaf definition;
10. conditional requiredness based on door type;
11. referential integrity rules;
12. conditional `data-wall` requirements for utility types;
13. prohibited redundant geometric attributes;
14. controlled `data-x-*` and `x-*` namespaces for extensions;
15. validator error categories;
16. unambiguous presentation/semantic separation.

---

# 28. Intentionally unsupported or not yet fully modeled cases

The 2.1 core schema intentionally does not attempt to describe every architectural case.

The following are not yet part of the formal core model:

- multiple levels;
- diagonal plan-view wall;
- curved wall;
- variable wall height within a single wall;
- sloped ceiling;
- double-leaf hinged door;
- folding door;
- detailed leaf and track geometry of a sliding door;
- detailed sash geometry of a multi-sash window;
- wall layer structure;
- detailed 3D profile of a door/window frame;
- detailed step geometry of stairs.

These may be added by a later version with an explicit schema.

The parser MUST NOT infer their geometry from visual shape or name.

# 30. Final principle

In this system, the SVG is not an illustration, but a **canonical, structured apartment model**.

If any visual interpretation, CSS style, reference photo, or generated image contradicts the geometry of the schema-conformant SVG, then the geometric data in the SVG takes precedence.

The parser may not guess.

If information is required by the specification but is missing, the correct result is a **validation error**, not an implicit assumption.

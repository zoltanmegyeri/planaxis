# 1. Cél és hatókör

Ez a dokumentum egy lakás pontos, géppel értelmezhető, kézzel is szerkeszthető SVG-alapú geometriai és szemantikai modelljének **normatív specifikációja**.

A specifikáció célja, hogy egy érvényes SVG dokumentum értelmezése során:

- ne legyen szükség vizuális találgatásra;
- ne legyen szükség természetes nyelvi következtetésre;
- ugyanazt az SVG-t két egymástól független implementáció ugyanúgy értelmezze;
- minden strukturális elem attribútumkészlete, adattípusa és jelentése egyértelmű legyen;
- a geometriai és referenciális hibák automatikusan validálhatók legyenek;
- a megjelenítés (`style`, CSS, színek, stroke-ok) semmilyen módon ne befolyásolja a geometriai vagy szemantikai értelmezést.

A formátum jelen verziója egyetlen lakásszintet kezel.

# 2. Normatív kulcsszavak

A dokumentumban az alábbi kifejezések normatív jelentésűek:

- **KÖTELEZŐ / MUST** – a szabály megsértése érvénytelen dokumentumot eredményez.
- **TILOS / MUST NOT** – az adott konstrukció nem használható.
- **AJÁNLOTT / SHOULD** – erősen javasolt, de indokolt esetben eltérés megengedett.
- **NEM AJÁNLOTT / SHOULD NOT** – kerülendő, de indokolt esetben megengedett.
- **OPCIONÁLIS / MAY** – szabadon használható.

Ha egy példa és egy normatív szabály ellentmond egymásnak, a normatív szabály az elsődleges.

# 4. Alapvető modellezési elvek

## 4.1. Egyetlen geometriai igazságforrás

A pontos 2D geometria kizárólag az SVG geometriai attribútumaiból származik.

Például:

```xml
<rect x="100" y="200" width="12" height="412" />
```

A fenti elem 12 × 412 cm-es téglalapot jelent.

Ugyanezt a méretet külön `data-width`, `data-length`, `data-depth` vagy hasonló attribútumban tárolni TILOS.

## 4.2. 1 SVG unit = 1 cm

Minden numerikus SVG-koordináta és geometriai méret centiméterben értendő.

## 4.3. Koordinátarendszer

A 2D rendszer:

- `+X` = jobbra;
- `+Y` = lefelé.

A 3D rendszer:

- `+X` = jobbra;
- `+Y` = lefelé;
- `+Z` = felfelé.

## 4.4. Transzformációk tilalma

A szemantikai modell részét képező elemeken és azok szülőcsoportjain a `transform` attribútum TILOS.

`transform` kizárólag az `annotations` csoporton belül használható.

## 4.5. CSS és megjelenítés

A következők megengedettek:

- belső `<style>`;
- külső CSS `<?xml-stylesheet ...?>` processing instructionnel;
- `class`;
- `style`;
- `fill`;
- `stroke`;
- egyéb kizárólag vizuális SVG/CSS tulajdonságok.

Ezek **nem részei a szemantikai modellnek**, ezért parser vagy validator nem használhatja őket geometriai vagy funkcionális következtetésre.

# 5. Lexikai adattípusok

Az alábbi típusnevek a specifikáció további részeiben normatív rövidítések.

## 5.1. `Id`

Formátum:

```text
[A-Za-z][A-Za-z0-9._-]*
```

Példák:

```text
wall-living-left
window-01
camera.main
```

Az `id` dokumentumszinten egyedi MUST legyen.

## 5.2. `Ref`

Egy másik elem `id` értékére mutató karakterlánc.

A hivatkozott elemnek léteznie kell, és a megfelelő `data-kind` típusúnak kell lennie.

## 5.3. `Number`

Tízes számrendszerű véges szám:

```text
-?[0-9]+(\.[0-9]+)?
```

TILOS:

- exponenciális alak (`1e3`);
- `NaN`;
- `Infinity`;
- mértékegység az értékben (`12cm`).

## 5.4. `PositiveNumber`

`Number`, amelyre:

```text
value > 0
```

## 5.5. `NonNegativeNumber`

`Number`, amelyre:

```text
value >= 0
```

## 5.6. `Boolean`

Pontosan az alábbi két érték egyike:

```text
true
false
```

## 5.7. `Angle360`

`Number`, amelyre:

```text
0 <= value < 360
```

## 5.8. `PitchAngle`

`Number`, amelyre:

```text
-90 < value < 90
```

## 5.9. Geometriai tolerancia

A geometriai összehasonlítás normatív toleranciája:

```text
EPSILON = 0.01 cm
```

Két koordináta geometriailag egyenlő, ha:

```text
abs(a - b) <= EPSILON
```

A parser AJÁNLOTT, hogy a bemeneti decimális értékeket pontos decimális aritmetikával kezelje.

## 5.10. `Latitude`

WGS84 földrajzi szélesség decimális fokban.

Típusa `Number`, és:

```text
-90 <= value <= 90
```

Jelkonvenció:

```text
value > 0  -> északi szélesség
value < 0  -> déli szélesség
value = 0  -> Egyenlítő
```

Fokjel vagy égtájbetű (`N`, `S`) az értékben TILOS.

## 5.11. `Longitude`

WGS84 földrajzi hosszúság decimális fokban.

Típusa `Number`, és:

```text
-180 <= value <= 180
```

Jelkonvenció:

```text
value > 0  -> keleti hosszúság
value < 0  -> nyugati hosszúság
value = 0  -> greenwichi kezdőmeridián
```

Fokjel vagy égtájbetű (`E`, `W`) az értékben TILOS.

A `-180` és `180` ugyanazt a meridiánt jelöli; új dokumentumban a `180` kanonikus alak AJÁNLOTT.

## 5.12. `ElevationMeters`

A hely tengerszint feletti magassága **méterben, közepes tengerszinthez (MSL – mean sea level) viszonyítva**.

Típusa `Number`.

Negatív érték megengedett tengerszint alatti hely esetén.

Az érték nem WGS84 ellipszoidmagasság. Ha a forrás kizárólag ellipszoidmagasságot szolgáltat, azt a dokumentumba írás előtt MSL magassággá kell konvertálni.

## 5.13. `TimeZoneId`

Nem üres karakterlánc, amely egy IANA Time Zone Database által definiált zónaazonosító.

Példa:

```text
Europe/Budapest
America/New_York
Asia/Tokyo
```

Fix UTC-offset (`+02:00`, `UTC+2`) időzónaazonosító helyett TILOS.

A `TimeZoneId` civil időszámítási szabályokat jelöl, ezért a történeti és jövőbeli UTC-offset a dátumtól függhet.

# 6. Dokumentumszerkezet

Egy konform dokumentum minimális struktúrája:

```xml
<?xml version="1.0" encoding="UTF-8"?>

<svg
    xmlns="http://www.w3.org/2000/svg"
    viewBox="..."
    data-schema="apartment-svg"
    data-schema-version="2.1"
    data-unit="cm">

    <metadata>...</metadata>

    <g id="spaces">...</g>
    <g id="walls">...</g>
    <g id="windows">...</g>
    <g id="doors">...</g>
    <g id="fixed-elements">...</g>
    <g id="utilities">...</g>
    <g id="cameras">...</g>
    <g id="annotations">...</g>

</svg>
```

## 6.1. Kötelező főcsoportok

A következő nyolc csoport mindegyikének pontosan egyszer kell szerepelnie:

| `id` | Funkció |
|---|---|
| `spaces` | funkcionális zónák |
| `walls` | falak |
| `windows` | ablakok |
| `doors` | ajtónyílások |
| `fixed-elements` | fix építészeti és gépészeti elemek |
| `utilities` | elektromos és informatikai pontok |
| `cameras` | definiált kamerák |
| `annotations` | kizárólag emberi olvasást segítő grafika |

Üres csoport megengedett.

A csoportok sorrendje nem szemantikus, de a fenti sorrend AJÁNLOTT.

## 6.2. Egyéb megengedett gyökérszintű SVG elemek

A következő nem szemantikai elemek opcionálisan megjelenhetnek közvetlenül az `<svg>` alatt:

```text
style
defs
title
desc
```

Ezek tartalma a core geometriai modell szempontjából figyelmen kívül hagyandó.

Külső CSS az XML dokumentum elején elhelyezett `xml-stylesheet` processing instructionnel is hivatkozható.

## 6.3. Ismeretlen főcsoport

Ismeretlen közvetlen `<g>` gyermek schema-hiba.

Kísérleti kiterjesztés kizárólag ilyen azonosítóval használható:

```text
x-*
```

Például:

```xml
<g id="x-furniture-prototype">...</g>
```

Egy 2.1 parser az ilyen csoport tartalmát figyelmen kívül hagyhatja.

# 8. `<metadata>` blokk

Normatív minimális struktúra:

```json
{
  "schema": "apartment-svg/2.1",
  "project": {
    "name": "Apartment renovation",
    "units": "cm"
  },
  "coordinateSystem": {
    "x": "right",
    "y": "down",
    "z": "up",
    "headingDegrees": {
      "0": "+x",
      "90": "+y",
      "180": "-x",
      "270": "-y"
    }
  },
  "level": {
    "id": "level-0",
    "baseZ": 0,
    "defaultCeilingHeight": 242
  }
}
```

Ugyanez opcionális földrajzi helyadatokkal:

```json
{
  "schema": "apartment-svg/2.1",
  "project": {
    "name": "Apartment renovation",
    "units": "cm"
  },
  "coordinateSystem": {
    "x": "right",
    "y": "down",
    "z": "up",
    "headingDegrees": {
      "0": "+x",

    "id": "level-0",
```

| JSON útvonal | Típus | Kötelező | Korlát |
|---|---|---:|---|
| `schema` | string | igen | `apartment-svg/2.1` |
| `project.name` | non-empty string | igen | projekt neve |
| `project.units` | enum | igen | `cm` |
| `coordinateSystem.x` | enum | igen | `right` |
| `coordinateSystem.y` | enum | igen | `down` |
| `coordinateSystem.z` | enum | igen | `up` |
| `coordinateSystem.headingDegrees.0` | enum | igen | `+x` |
| `coordinateSystem.headingDegrees.90` | enum | igen | `+y` |
| `coordinateSystem.headingDegrees.180` | enum | igen | `-x` |
| `coordinateSystem.headingDegrees.270` | enum | igen | `-y` |
| `level.id` | `Id` | igen | jelen verzióban egy szint |
| `level.baseZ` | `Number` | igen | tipikusan `0` |
| `level.defaultCeilingHeight` | `PositiveNumber` | igen | cm |

A `project.units` és a gyökér `data-unit` értékének egyeznie kell.

## 8.2. Opcionális földrajzi hely és tájolás

A dokumentum opcionálisan tartalmazhat egy `location` objektumot.

Példa:

```json
"location": {
  "latitude": 47.4979,
  "longitude": 19.0402,
  "elevationMeters": 105,
  "timeZone": "Europe/Budapest",
  "northHeading": 270
}
```

A `location` objektum a lakás **állandó földrajzi és tájolási adatait** írja le. Nem renderelési állapot.

### 8.2.1. Attribútumséma

| JSON útvonal | Típus | Kötelező | Jelentés / korlát |
|---|---|---:|---|
| `location.latitude` | `Latitude` | feltételes | `location` esetén kötelező; WGS84 szélesség |
| `location.longitude` | `Longitude` | feltételes | `location` esetén kötelező; WGS84 hosszúság |
| `location.northHeading` | `Angle360` | feltételes | `location` esetén kötelező; a valódi észak iránya az SVG koordinátarendszerében |
| `location.elevationMeters` | `ElevationMeters` | nem | MSL tengerszint feletti magasság méterben |
| `location.timeZone` | `TimeZoneId` | nem | a hely civil időzónája |

A teljes `location` objektum OPCIONÁLIS.

Ha a `location` objektum jelen van, akkor a következő három mező együttesen KÖTELEZŐ:

```text
latitude
longitude
northHeading
```

`elevationMeters` és `timeZone` opcionálisak.

A parsernek TILOS hiányzó `elevationMeters` vagy `timeZone` értéket a koordinátákból automatikusan kikövetkeztetnie és azt a kanonikus modell részeként kezelnie.

### 8.2.2. `northHeading` pontos jelentése

A `northHeading` a **földrajzi valódi észak (true north)** irányát adja meg az apartment SVG felülnézeti koordinátarendszerében.

Nem mágneses északot jelöl.

Ugyanazt a heading-konvenciót használja, mint a kamerák:

```text
0°   = +X = jobbra
90°  = +Y = lefelé
180° = -X = balra
270° = -Y = felfelé
```

Például:

```json
"northHeading": 270
```

jelentése: a valódi észak az SVG-n felfelé, azaz `-Y` irányban található.

A `northHeading` az SVG teljes koordinátarendszerére globálisan érvényes.

### 8.2.3. Földrajzi azimut átalakítása SVG headinggé

A specifikációban a földrajzi azimut konvenciója:

```text
0°   = true north
90°  = east
180° = south
270° = west
```

Az azimut az óramutató járásával megegyező irányban nő.

Ha:

```text
N = location.northHeading
A = geographicAzimuth
```

akkor az adott földrajzi irány SVG headingje:

```text
svgHeading = normalize360(N + A)
```

ahol:

```text
normalize360(x) = ((x % 360) + 360) % 360
```

Példa:

```text
northHeading = 270°
solarAzimuth = 90°   (kelet)

svgHeading = normalize360(270 + 90)
           = 0°
           = +X
```

### 8.2.4. Napirány levezetése 3D koordinátákra

Ha egy külső csillagászati algoritmus a renderelt pillanatra meghatározza:

```text
A = solar azimuth
E = solar elevation angle
```

akkor először:

```text
H = normalize360(location.northHeading + A)
```

Az SVG/3D koordinátarendszerben a megfigyelőtől a Nap felé mutató egységvektor:

```text
sunVector.x = cos(E) * cos(H)
sunVector.y = cos(E) * sin(H)
sunVector.z = sin(E)
```

ahol a trigonometrikus függvények argumentumát radiánban kell kiértékelni.

A fenti `sunVector` **a jelenettől a Nap felé** mutat.

A Napból a jelenet felé érkező fénysugár iránya ennek ellentettje:

```text
incomingLightDirection = -sunVector
```

Ez a definíció rendererfüggetlen; egy Three.js vagy más renderelő motor saját fényobjektumára ezt a szemantikát kell megfelelően leképezni.

### 8.2.5. Dátum és idő nem része az SVG-nek

A dátum és az idő **nem a lakás állandó tulajdonsága**, ezért a kanonikus apartment SVG metadata részében nem tárolandó.

A renderelési / szimulációs kérés külön futásidejű paraméterként adja meg a vizsgált pillanatot.

AJÁNLOTT formátum egy offsetet is tartalmazó ISO 8601 időpont, például:

```text
2026-10-18T17:42:00+02:00
```

Ha a futásidejű kérés csak helyi civil dátumot és időt ad meg UTC-offset nélkül, akkor `location.timeZone` szükséges annak egyértelmű UTC-pillanattá alakításához.

Ha `location.timeZone` hiányzik, offset nélküli helyi időt a renderernek TILOS találgatással UTC-pillanattá alakítania.

### 8.2.6. Solar-aware képesség

A geometriai napállás számításához legalább a következő adatok szükségesek:

```text
location.latitude
location.longitude
location.northHeading
render-time date/time as an unambiguous instant
```

Az `elevationMeters` használható a nagyobb pontosságú napállás-, refrakció- vagy atmoszférikus modellhez.

A `timeZone` nem szükséges, ha a renderelési időpont már egyértelmű UTC-pillanatot vagy explicit UTC-offsetet tartalmaz; helyi civil idő bevitelekor azonban szükséges.

A Nap **geometriai helyzete** (azimut és magassági szög) determinisztikusan levezethető a megfelelő csillagászati modell segítségével.

A közvetlen napfény **tényleges színe és intenzitása** nem vezethető le kizárólag az apartment SVG-ből, mert azt többek között a légköri és időjárási állapot is befolyásolja.

Egy renderer használhat explicit clear-sky vagy más atmoszférikus modellt, de:

- a használt modell a renderelő rendszer konfigurációja, nem az apartment SVG geometriája;
- tényleges időjárási adat hiányában a renderer nem állíthatja, hogy valós meteorológiai állapotot reprodukál;
- a fény színét és intenzitását nem szabad kanonikus geometriai tényként visszaírni az SVG-be.

### 8.2.7. Hiányzó `location`

Ha `location` nincs megadva:

- a dokumentum ettől még teljesen schema-konform lehet;
- a parser nem feltételezhet alapértelmezett földrajzi helyet;
- a parser nem feltételezhet alapértelmezett északi irányt;
- a földrajzilag valós napállásra épülő renderelés csak külön, futásidőben megadott helyadatokkal végezhető.

## 8.3. Metadata kiterjesztések

A fenti objektumokban ismeretlen kulcs TILOS, kivéve ha a kulcs neve `x-` előtaggal kezdődik. Az `x-*` metadata-kulcs nem módosíthatja a core szemantikát.

# 9. Közös szabályok a szemantikai elemekhez

Minden szemantikai elem:

1. rendelkezik egyedi `id` attribútummal;
2. rendelkezik `data-kind` attribútummal;
3. közvetlen gyermeke a hozzá tartozó főcsoportnak;
4. nem rendelkezik `transform` attribútummal.

Szemantikai elemek egymásba ágyazása TILOS.

Például falon belül újabb `<rect>` nem lehet.

## 9.1. Prezentációs attribútumok

A normatív táblázatokban nem felsorolt, szabványos SVG prezentációs attribútumok — például `class`, `style`, `fill`, `stroke`, `opacity` — megengedettek, de a core parsernek figyelmen kívül kell hagynia őket.

Geometriát módosító, de a jelen specifikációban nem engedélyezett SVG attribútum vagy konstrukció nem használható szemantikai következtetésre.

## 9.2. Kiterjesztési attribútumok

Ismeretlen `data-*` attribútum TILOS, kivéve ha neve:

```text
data-x-*
```

Például:

```xml
data-x-source="survey-2026"
```

A `data-x-*` attribútumot a core parser figyelmen kívül hagyja.

# 10. Státusz típus

Ahol a specifikáció `data-status` attribútumot engedélyez, annak típusa:

```text
fixed | modifiable | proposal
```

Jelentés:

| Érték | Jelentés |
|---|---|
| `fixed` | a jelenlegi modellben nem változtatható |
| `modifiable` | meglévő, de tervezés során módosítható / bontható / áthelyezhető |
| `proposal` | nem meglévő, hanem tervezett új elem |

A `status` **tervezési státusz**, nem geometriai típus.

# 11. `spaces` – funkcionális zónák

## 11.1. Engedélyezett elem

Kizárólag:

```xml
<polygon>
```

## 11.2. Attribútumséma

| Attribútum | Típus | Kötelező | Jelentés |
|---|---|---:|---|
| `id` | `Id` | igen | egyedi azonosító |

### Ha a fal `data-axis="y"`


```text

```

A 2.1 core séma küszöb nélküli ajtót feltételez.

## 14.7. A `hinge` pont pontos definíciója

A `hinge` pont a pántolt ajtó forgástengelyének alaprajzi vetülete.

A pont:

- a hordozó fal középvonalán van;
- az ajtónyílás hosszanti irányú két végpontjának egyikével esik egybe.

### Vízszintes fal (`data-axis="x"`)

```text
centerY = wall.y + wall.height / 2
```

A hinge pontosan az alábbi kettő egyike:

```text
(door.x,              centerY)
(door.x + door.width, centerY)
```

### Függőleges fal (`data-axis="y"`)

```text
centerX = wall.x + wall.width / 2
```

A hinge pontosan az alábbi kettő egyike:

```text
(centerX, door.y)
(centerX, door.y + door.height)
```

Más hinge-pozíció schema-geometriai hiba.

## 14.8. A zárt ajtólap implicit geometriája

A zárt ajtólap külön attribútumokkal nincs tárolva.

A hinge alapján egyértelműen meghatározható a zárt állapot szabad végpontja.

### Vízszintes fal

Ha:

```text
hinge = (door.x, centerY)
```

akkor:

```text
closedFreeEnd = (door.x + door.width, centerY)
```

Ha:

```text
hinge = (door.x + door.width, centerY)
```

akkor:

```text
closedFreeEnd = (door.x, centerY)
```

### Függőleges fal

Ha:

```text
hinge = (centerX, door.y)
```

akkor:

```text
closedFreeEnd = (centerX, door.y + door.height)
```

Ha:

```text
hinge = (centerX, door.y + door.height)
```

akkor:

```text
closedFreeEnd = (centerX, door.y)
```

## 14.9. Az `open-leaf` pont pontos definíciója

Az `open-leaf` pont a **90°-ra teljesen kinyitott ajtólap szabad végpontja**.

A hinge pont nem mozdul.

Az ajtólap hossza:

```text
leafLength = openingWidth
```

Kötelező:

```text
distance(hinge, openLeaf) == leafLength
```

és a nyitott ajtólap merőleges a hordozó fal hosszanti tengelyére.

### Vízszintes fal

Kötelező:

```text
openLeaf.x == hinge.x
abs(openLeaf.y - hinge.y) == leafLength
```

Tehát pontosan két geometriailag lehetséges 90°-os állapot van:

```text
(hinge.x, hinge.y - leafLength)
(hinge.x, hinge.y + leafLength)
```

### Függőleges fal

Kötelező:

```text
openLeaf.y == hinge.y
abs(openLeaf.x - hinge.x) == leafLength
```

Tehát pontosan két geometriailag lehetséges 90°-os állapot van:

```text
(hinge.x - leafLength, hinge.y)
(hinge.x + leafLength, hinge.y)
```

## 14.10. Nyitási irány

A nyitási irány kizárólag a `hinge` és `open-leaf` geometriai adataiból következik.

Például vízszintes fal esetén:

```text
openLeaf.y < hinge.y  -> az ajtó -Y oldalra nyílik
openLeaf.y > hinge.y  -> az ajtó +Y oldalra nyílik
```

Függőleges fal esetén:

```text
openLeaf.x < hinge.x  -> az ajtó -X oldalra nyílik
openLeaf.x > hinge.x  -> az ajtó +X oldalra nyílik
```

A specifikációban TILOS nézőpontfüggő `left/right/inward/outward` attribútumot tárolni.

## 14.11. Ajtónyitási ív

Az ajtónyitási ív:

- levezetett, prezentációs geometria;
- nem része az igazságforrásnak;
- kizárólag az `annotations` csoportban tárolható vagy rendereléskor generálható.

Az ív középpontja a hinge, sugara `leafLength`, kezdő- és végiránya a zárt és a nyitott ajtólap iránya.

ha az érték közvetlenül és egyértelműen származtatható a normatív SVG geometriából.

A cél: ugyanaz a geometriai tény pontosan egy helyen legyen tárolva.

# 22. Kanonikus értelmezési sorrend

Egy parser az alábbi logikai sorrend szerint dolgozzon:

1. XML parse.
2. Root attribútumok validálása.
3. Metadata parse és validálás.
4. Kötelező főcsoportok ellenőrzése.
5. Egyedi `id` index felépítése.
6. Elemtípusok schema-validálása.
7. Referenciák feloldása.
8. Falgeometria és wall axis validálása.
9. Nyílászáró–fal kapcsolatok validálása.
10. Ajtó hinge/open-leaf invariánsok validálása.
11. Zóna topológia validálása.
12. Fixed-elements validálása.
13. Utilities validálása.
14. Kamerák validálása.
15. Átfedési szabályok vizsgálata.
16. Csak ezután építhető 3D modell.

# 23. Validator hibakategóriák

AJÁNLOTT hibakód-formátum:

```text
APSVG-<CATEGORY>-<NUMBER>
```

Példák:

| Kód | Jelentés |
|---|---|
| `APSVG-XML-001` | hibás XML |
| `APSVG-ROOT-001` | hiányzó root attribútum |
| `APSVG-ID-001` | duplikált ID |
| `APSVG-REF-001` | törött referencia |
| `APSVG-WALL-001` | hibás `data-axis` geometria |
| `APSVG-WINDOW-001` | ablak nem fedi pontosan a falvastagságot |
| `APSVG-DOOR-001` | hibás hinge pont |
| `APSVG-DOOR-002` | hibás open-leaf pont |
| `APSVG-ZONE-001` | önmetsző zóna |
| `APSVG-CAMERA-001` | kamera falban |

A validator hibaüzenete tartalmazza legalább:

- hibakód;
- érintett elem `id`;
- attribútum vagy geometriai szabály;
- tényleges érték;
- elvárt feltétel.

# 24. Normatív ajtópéldák

## 24.1. Függőleges fal, hinge fent, nyitás balra

Fal:

```xml
<rect
    id="wall-bedroom-right"
    x="420"
    y="100"
    width="12"
    height="400"
    data-kind="wall"
    data-axis="y"
    data-class="interior"
    data-status="fixed"
/>
```

Ajtó:

```xml
<rect
    id="door-bedroom-01"
    x="420"
    y="300"
    width="12"
    height="90"
    data-kind="door"
    data-wall="wall-bedroom-right"
    data-door-type="hinged"
    data-opening-height="210"
    data-hinge-x="426"
    data-hinge-y="300"
    data-open-leaf-x="336"
    data-open-leaf-y="300"
    data-status="fixed"
/>
```

Levezetés:

```text
wall centerX = 420 + 12 / 2 = 426
leafLength   = 90

hinge        = (426, 300)
openLeaf     = (426 - 90, 300)
             = (336, 300)
```

Érvényes.

## 24.2. Függőleges fal, hinge lent, nyitás jobbra

```xml
data-hinge-x="426"
data-hinge-y="390"

data-open-leaf-x="516"
data-open-leaf-y="390"
```

Levezetés:

```text
leafLength = 90
516 = 426 + 90
```

Érvényes.

## 24.3. Vízszintes fal, hinge bal, nyitás felfelé

Tegyük fel:

```text
door = x:200, y:100, width:90, height:12
wall axis = x
wall centerY = 106
```

A helyes adatok:

```xml
data-hinge-x="200"
data-hinge-y="106"

data-open-leaf-x="200"
data-open-leaf-y="16"
```

mert:

```text
16 = 106 - 90
```

## 24.4. Érvénytelen hinge

```xml
data-hinge-x="426"
data-hinge-y="320"
```

függőleges fal esetén hibás, mert a hinge nem az ajtónyílás felső vagy alsó hosszanti végén található.

## 24.5. Érvénytelen open-leaf

```xml
data-hinge-x="426"
data-hinge-y="300"

data-open-leaf-x="350"
data-open-leaf-y="320"
```

hibás, mert:

- az ajtólap nem merőleges a falra;
- a távolság nem pontosan a nyílásszélesség;
- az állapot nem 90°-os referenciaállapot.

# 27. Verzióváltozások

## 27.1. Változások a 2.0 verzióhoz képest

A 2.1 verzió kizárólag az opcionális földrajzi hely- és tájolási metadata formális támogatásával bővíti a 2.0 specifikációt.

Újdonságok:

1. `Latitude`, `Longitude`, `ElevationMeters` és `TimeZoneId` lexikai típusok;
2. opcionális `metadata.location` objektum;
3. kötelező `latitude`, `longitude` és `northHeading`, ha a `location` objektum jelen van;
4. opcionális `elevationMeters` és `timeZone`;
5. `northHeading` explicit true-north szemantikája;
6. földrajzi azimut → SVG heading normatív transzformáció;
7. napirány → 3D egységvektor normatív transzformáció;
8. a render-time dátum/idő és az állandó lakásmetadata explicit szétválasztása;
9. szabály az offset nélküli helyi idő és `timeZone` kapcsolatára;
10. explicit határ a determinisztikus napgeometria és az atmoszférikus fényintenzitás/szín modellezése között.

A 2.0 minden más, a fenti bővítéstől független szabálya változatlanul érvényes.

## 27.2. Változások az 1.0 verzióhoz képest

A 2.0 verzió legfontosabb szigorításai:

1. normatív `MUST / MUST NOT / SHOULD / MAY` szemantika;
2. explicit lexikai adattípusok;
3. explicit `EPSILON`;
4. kötelező főcsoport-séma;
5. kötelező és feltételes attribútumtáblák;
6. explicit `data-axis` a falakon;
7. pontos ablak–fal geometriai invariánsok;
8. `data-door-type` bevezetése;
9. matematikailag pontos hinge és open-leaf definíció;
10. feltételes kötelezőség ajtótípus alapján;
11. referenciális integritási szabályok;
12. utility típusok feltételes `data-wall` követelményei;
13. tiltott redundáns geometriai attribútumok;
14. kiterjesztések szabályozott `data-x-*` és `x-*` névterei;
15. validator hibakategóriák;
16. egyértelmű prezentációs/szemantikai szétválasztás.

# 28. Tudatosan nem támogatott vagy még nem teljesen modellezett esetek

A 2.1 core séma szándékosan nem próbál minden építészeti esetet leírni.

Nem része még a formális core modellnek:

- több szint;
- ferde alaprajzi fal;
- íves fal;
- változó falmagasság egyetlen falon belül;
- ferde mennyezet;
- kétszárnyú pántolt ajtó;
- harmonikaajtó;
- tolóajtó részletes szárny- és síngeometriája;
- többszárnyú ablak részletes szárnygeometriája;
- fal rétegrend;
- nyílászáró tok részletes 3D profilja;
- lépcső részletes fokgeometriája.

Ezeket későbbi verzió explicit sémával bővítheti.

A parsernek TILOS ezek geometriáját vizuális alakból vagy névből kikövetkeztetnie.

# 30. Végső alapelv

Az SVG ebben a rendszerben nem illusztráció, hanem **kanonikus, strukturált lakásmodell**.

Ha bármely vizuális interpretáció, CSS-stílus, referenciafotó vagy generált kép ellentmond a schema-konform SVG geometriájának, akkor az SVG geometriai adata az elsődleges.

A parser nem találgathat.

Ha egy információ a specifikáció szerint szükséges, de hiányzik, a helyes eredmény **validációs hiba**, nem implicit feltételezés.
